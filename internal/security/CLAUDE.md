# Jamf Security Cloud

## Two Halves, Two Auth Paths

Security Cloud commands live under `security` and split into two fundamentally different auth paths:

- **Radar API** (`api.wandera.com`) — hand-rolled client in `internal/security`; Basic-login-for-JWT exchange; no product Go SDK
- **Platform gateway** (`/securitycloud/…`) — platform client-credentials; six specs from `jamfplatform-go-sdk`'s published `api/`; generated by the Platform generator into `internal/commands/platform/generated/`, then wired under `security` in `security.go`

Every generated command carries `jamf:api` (`platform-gateway` or `radar`) and a `Short` suffix — `(Security Cloud · platform gateway)` vs `(Security Cloud · Radar API)` — so `security <TAB>` shows which API serves each command. `TestSecurityCommandsDeclareTheirAPI` fails if a command is emitted without the annotation. `security setup` declares neither — it writes credentials and calls no API.

## Radar API (Wandera)

Uses a hand-rolled client in `internal/security`. Auth: `POST /v1/login` with `base64(clientId:clientSecret)` in the `Authorization: Basic` header → a 15-minute JWT. Critically, each of the three APIs — Risk, Device Lifecycle, Shared Signals & Events (SSE) — is provisioned as its own "Security Integration" in the Radar portal with its own application ID/secret, and the resulting JWT is scoped to exactly one API via its `aud` claim. `Client` tracks three independent credential pairs and token caches (`DoExpectRisk`/`DoExpectLifecycle`/`DoExpectSSE`). Any subset may be configured; commands for an unconfigured API fail with a "run security setup" hint rather than the whole product refusing to start.

Risk and Device Lifecycle share one host (`api.wandera.com`, which also serves `/v1/login`); SSE lives on `sse.jamf.com` per its own OpenID SSE framework discovery document. Unlike Pro/Protect/School, there's no per-tenant URL — tenancy is carried inside the JWT's `customer_id` claim, so `security setup` never prompts for a URL (env/profile overrides exist for `--url`/`JAMFSECURITY_URL`/`JAMFSECURITY_SSE_URL` in case Jamf ever stands up regional or sandbox hosts).

**Commands are generator-owned**, same as Platform — the eleven total operations across three specs are hand-mapped (`securityOpsByFile` in `generator/parser/security.go`), not tag/family auto-detected, because they span wildly different shapes (a paginated list, singleton-style get/update/delete, bulk actions with no `{id}` in their path) that are too few and irregular for generic detection. Commands: `risk` (`list`/`override`), `device-lifecycle` (`purge` — destructive, `{customerId}` filled from the Device Lifecycle JWT at request time), `stream` (SSE singleton get/update/delete), `status` (get/update), `verification` (`trigger`), `jwks`/`well-known` (SSE discovery, read-only). No name-to-ID resolution.

**`resolveSecurityClient`** builds the platform SDK client independently of the scoped pairs, so a profile may carry either credential set or both; the product only refuses to start when neither is configured.

**`topLevelNamespace` fix — SIGSEGV from `pro report security`.** `resolveProduct` (`root.go`) returned on the first product-named *ancestor*, so `pro report security` resolved to product `security`; `PersistentPreRunE` returned early on that branch without building `cliCtx.Client`, and `runReportSecurity` dereferenced a nil one. It used to fail safely because `resolveSecurityClient` found no Radar credentials — until `securityPlatformSDKClient` made that path succeed from generic env vars, turning a clean exit 2 into a SIGSEGV. `topLevelNamespace` now answers from the ancestor that is a direct child of the root, not the deepest match.

## Gateway-Served Half

Six specs, 52 operations wired under `security` in `security.go` — the same namespace as the Wandera-served commands, because it is one product to whoever is typing, and `pro` already mixes two auth paths under one namespace.

**Specs come from the SDK, not from `public-apis-oas`.** Drop `jamfplatform-go-sdk`'s published `api/securitycloud_*.json` into `specs/.platform-source/`, then `make sync-platform-specs`. The upstream `-beta` specs are wrong in ways only wire probing revealed; corrections live in the SDK's `tools/generate/config.json`. The SDK publishes them as OpenAPI extensions this generator reads, so no override table is duplicated here.

**`serviceSegment` mixes both URL shapes.** `TestServiceSegment` pins both: Platform specs are v1807 and carry no `/api/` in `servers[0].url`, while Security Cloud specs still declare it — one spec drop legitimately mixes them.

## `device-groups` History

**`platformUnroutedOps` is empty.** Build v1865 declared `PUT /v2/groups/{groupId}` as successor to the v1 PUT, but it answered `403 BAD_PERMISSIONS` until `authorization-policies#265` deployed 2026-09-03, then `404 NOT_FOUND` (handler bug) until 2026-09-04. Re-probed 2026-09-05: `PUT /v2/groups/{groupId}` answers **204**; verified end to end through the CLI. Build v2082 then withdrew `GET /v1/groups` and `PUT /v1/groups/{groupId}` outright — making removal of the `platformUnroutedOps` entry compulsory. With the entry still in place the resource shipped **no update command at all**; `TestSecurityCloudSpecParity` caught it as 51 subcommands vs 52 declared operations.

The hold's end condition was written as "lift when the v2 PUT answers 2xx, not when it stops 403ing" — and the two events were different. **A 403 clearing is not the same as the capability arriving.** This is the reasoning the table's comment preserves for the next entry.

`create` and `delete` stay on v1; `list` and `update` are v2.

**Only the implicit "Default Group" is returned without an ID.** `GroupListItem` declares `id` and requires only `name`; the Default Group carries no `id`. `platform.ResolveIDByName` now reports "the list returns no ID for the items it matched" rather than "not found" when a name matches and no `id` is returned, distinguishing a server-side gap from a typo.

## `enrollment-activation-profiles` Namespace Collision Fix

Two specs tag a resource `activation-profiles` (enrollment + UEM Connect). Both declare service `securitycloud`, so the one `securitycloud/activation-profiles` override folded them into a single resource. `platformResourceNameOverrides` is now tried `{namespace}/{name}` first, then `{service}/{name}`, then bare `{name}`. `platformNamespace` (`generator/parser/platform.go`) is the parser-side twin of the emitter's `namespaceFromPath`. `TestTwoSpecsSharingATagGetDistinctResourceNames` asserts resulting names and paths.

**`--name` suppressed on all three `{activationProfileId}` operations** (`platformNoNameLookup`): `ActivationProfile` carries only a `code`, so there is no name for `ResolveIDByName` to match, and `list` requires an `origin` parameter the resolver does not send.

## ZTNA Wire Facts

- **`href` returned `null` until `identityEncodingOnWrites`** was added: gateway drops `Location` and nulls `href` whenever response is gzipped. POST/PUT/PATCH now set `Accept-Encoding: identity`. Don't remove this transport.
- **`ztna-apps create`** requires `categoryName`; `--scaffold` renders `""` which the server explicitly rejects (`400 INVALID_FIELD categoryName: must not be blank`). Use `Uncategorized` or a real category name.
- **Predefined-derived apps return `name: null`**. `--name` cannot reach them. Use the ID.
- **`ztna-apps name` and `predefinedAppId` together** is accepted by the wire but silently drops the name (201, reads back `name: null`).
- **`ipsec.left.subnets`** capped at one element; two left subnets → `400 [INVALID_FIELD] ipsec "IPSec configuration is not valid."` with no field attribution.
- **`security.additionalProperties: false`** declared but unenforced — bogus key answers 201 and is silently dropped.
- **`recoveryDelayInSec`** enum of five integers (300/1800/3600/10800/28800) required on `ztna-grouped-gateways create`; `0` rejected.
- **`right.subnets`** returned in server's own order — an export/re-apply round trip is not byte-stable.
- `ztna-gateways patch` answers **nothing** (204); successful update prints nothing.

## UEM Connect Wire Facts

- `authStrategy` enum: `M2M`, `JAMF_PRO_OAUTH`, `BASIC`. With `M2M`, Security Cloud self-provisions an API role and integration on the named Jamf Pro — **that integration survives the connector's DELETE** (SDK test tenant had accumulated 97 enabled "JSC Connector" integrations against zero live connectors). Nothing in this CLI creates or cleans them up.
- `deviceSyncAuth` contains credentials; belongs in `--from-file`, not `--set` (shell history exposure).
- `uem-connectors create` answers **500** if `authStrategy` is absent — body validation runs before the 500 escalates, but the error comes from the wrong layer with no field attribution.
- A tenant holds at most one connector whatever its vendor; `create` on a tenant that already has one answers `409 CONNECTOR_CONFIG_ALREADY_EXISTS`.
- `refreshRateMinutes` enforces its enum on the wire; `deviceUnmanagedThreshold` is **silently ignored for `JAMF_PRO`** (204 regardless of value, always reads back as `0`).
- The vendor enum was wrong until build v1700: `WORKSPACE_ONE` → `AIRWATCH`, `MICLOUD` → `MOBILEIRONCLOUD`, `MICORE` → `MOBILEIRONCORE`.

## DNS Wire Facts

- `nameServers[].ip` must be **publicly routable** — `10.0.0.53` rejected as `NAMESERVER_IP_RESTRICTED`, `198.51.100.53` accepted. Inverse of ZTNA's left-subnets must-be-private rule.
- `dns-zones create` 422s (`GATEWAY_NOT_FOUND`, `NAMESERVER_IP_RESTRICTED`) are not documented in the spec.
- `--set` cannot express a top-level-array request body (DNS whole-list replaces); `--from-file` is the only route.

## Activation Profile Wire Facts (enrollment)

- **Create's declared `{id, href}` response body is never sent**; server answers `{"code": "…"}` with no `Location`.
- **Read model is a code and nothing else**: `get` returns `{"code": "…"}` only; `pause`/`resume` have no observable GET effect.
- **Delete is soft**: after `delete-multiple` answers 204, `get` and `list` still return the code.
- `pause`, `resume`, `delete-multiple` print **nothing** on success (204).
- `capabilities.networkSecurity` and `vulnerabilityManagement` must both be enabled or both disabled.
- `platforms` maxItems 2 applies **after** de-duplication; `["iOS","MAC","iOS"]` accepted.

## Scope and Auth

Gateway-served Security Cloud commands require platform client-credentials plus a Security Cloud tenant ID. The same `auth-method: platform` profile powers both halves; `resolveSecurityClient` builds the SDK client independently of the Radar pairs.

`security setup` owns the Radar application pairs only. It closes by pointing at `platform setup`, which owns the gateway credentials.

**Setup used to probe `content-categories` for an entitlement verdict.** That probe was unsound (wire-verified 2026-09-08: tenant credential answered `BAD_PERMISSIONS` on `/securitycloud/v1/categories` while environment credential answered 200 with 36 categories — so one 403 cannot establish entitlement absence), and removed. What survives is only the scope-ID check via `reportScopeIDProbe`.
