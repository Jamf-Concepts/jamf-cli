# Changelog fragments: one file per change

- **Status:** proposed, for review
- **Author:** Keaton Svoma
- **Reviewer:** Neil Martin, who cuts the releases
- **Date:** 2026-10-06

## Problem

Every PR that records a change adds a `### <Kind> — <title>` section at the top
of `## Unreleased` in `CHANGELOG.md`. So any two open PRs that both record a
change conflict in that file, whatever else they touch.

The organization ruleset "Source Branch Protections" makes that conflict
expensive. It applies to the default branch of every Jamf-Concepts repository,
and it sets two rules:

- `dismiss_stale_reviews_on_push`: any push to a PR dismisses its approval.
- `require_last_push_approval`: someone other than the last pusher must approve
  the latest push.

A conflict cannot be merged, and resolving it is a push. So each changelog
conflict costs a merge push, a new CI run and a new approval. On 2026-10-06,
#418, #419, #420 and #422 each added an entry, and most pairs of them conflicted
in `CHANGELOG.md` and in no other file. Resolving #419's conflict dismissed an
approval that Neil had already given.

## Goal

- Two PRs that each record a change never conflict because of the changelog.
- The rules for what goes in the changelog do not change.
- The release step is one command.
- No new third-party tool. Every contributor can run it with `go`.

## Non-goals

- What the changelog records. It stays the record of breaking changes, behaviour
  changes visible to a script, and removals. The full list of PRs stays in the
  GitHub release notes.
- The GitHub release notes. They stay generated by GitHub.
- A `## Unreleased` section that is current on `main` between releases. The
  organization rules require a PR for every change to `main`, so rebuilding the
  file after each merge would need a bot PR, and an approval, for every merge.

## Design

### Fragment files

- Each change is one Markdown file in `changelog.d/`.
- The file name only has to be unique. Use the branch name with `/` replaced by
  `-`, for example `changelog.d/fix-pro-setup-standard-no-privilege-management.md`.
  A PR number does not exist until the PR opens, so it is not used.
- A PR that makes two independent changes adds two files.
- The file holds what `CHANGELOG.md` holds today for one change:
  - The first non-empty line is `### <Kind> — <title>`.
  - The body follows. It can hold paragraphs, lists, tables, code blocks and
    `####` sub-headings, as entries do today.
- `<Kind>` is one of: `Breaking`, `Behaviour`, `Added`, `Deprecated`,
  `Changed`, `Removed`, `Fixed`. These are the kinds the file uses today, plus
  `Removed`, which #420 introduces.
- `changelog.d/README.md` states these rules for authors. The tools skip it.

### Assembly: `make changelog VERSION=vX.Y.Z`

The target runs `go run ./scripts/changelog -version vX.Y.Z`. The command does
these steps in order:

1. It refuses a `VERSION` that is not `vMAJOR.MINOR.PATCH`, or that is already a
   heading in `CHANGELOG.md`.
2. It reads every fragment and checks it with the same rules as the CI test
   below. It refuses the whole run if one fragment fails, and names that file.
3. If there are no fragments, it says so and changes nothing.
4. It writes a `## vX.Y.Z` section directly below `## Unreleased`. The sections
   are ordered by kind, in the order of the list above. Inside one kind they are
   ordered by the date the fragment first landed on `main`, oldest first, read
   from `git log --diff-filter=A`.
5. It deletes the fragments it wrote. `## Unreleased` stays as an empty heading.

A second run with the same version refuses at step 1, so the command cannot add
a section twice.

### Release flow

Today Neil publishes a GitHub release with the generated notes. The version
headings in `CHANGELOG.md` are added later, by hand; #411 added four of them in
one batch.

With fragments, a release is:

1. Create a branch `release/vX.Y.Z` from `main`.
2. Run `make changelog VERSION=vX.Y.Z`.
3. Read the diff, open a PR, get an approval, and squash-merge it.
4. Tag that merge and publish the release, as today.

If step 2 reports no fragments, steps 2 and 3 are skipped.

### Checks in CI

The validator code lives in `scripts/changelog` and serves both the command and
the test, so the two cannot disagree. `go test ./...` already covers `scripts/`.

- **New:** `TestChangelogFragmentsAreWellFormed` checks every file in
  `changelog.d/` except its README:
  - The name ends in `.md`, and the file is not empty.
  - The first non-empty line is `### <Kind> — <title>` with a known kind and a
    title.
  - No other `##` or `###` heading appears. `####` is allowed.
- **New:** the same test requires the `## Unreleased` section of `CHANGELOG.md`
  to be empty. This turns the convention into a check. A PR that still adds its
  entry to `CHANGELOG.md` fails CI with a message that names `changelog.d/`.
- **Unchanged:** `TestChangelogHeadingsAreUnique`. It already accepts an empty
  `## Unreleased`.
- **Changed:** `TestMCPPolicyTexts_NameEveryPayloadSecretSuffix` requires a
  policy sentence to appear in `CHANGELOG.md`. It reads `CHANGELOG.md` and every
  fragment together, so the sentence can live in either place.
- **Changed:** the failure messages in `invocation_sweep_test.go` and
  `generator/parser/subresource_test.go` say "CHANGELOG.md's migration table".
  They will say "the changelog's migration table", because the table can live in
  a fragment.

### Documentation

- `CHANGELOG.md`: the header paragraph says that unreleased changes live in
  `changelog.d/` until the release that assembles them.
- `README.md`: the Changelog section says the same, in one sentence.
- `changelog.d/README.md`: the rules for authors, with one example fragment.
- `.claude/skills/common-workflows/SKILL.md`: one line, so that agent sessions
  add a fragment and do not edit `CHANGELOG.md`.

## Cutover

One PR makes the change. It adds the command, the tests, the `Makefile` target
and the documentation. It also moves each section that is under `## Unreleased`
at that time into its own fragment, so that the next release assembles them
with everything else.

Each open PR that edits `## Unreleased` then fails the new check. Its author
moves the entry into a fragment the next time the PR takes in `main`. That PR
needs a push and a new approval at that point anyway, because the cutover
changes `CHANGELOG.md`. To keep this small, merge the PRs that are already
approved before the cutover lands. The cutover PR lists the open PRs that it
affects.

## Alternatives considered

- **`.gitattributes` with `merge=union` on `CHANGELOG.md`.** This needs no tool.
  But a merge driver runs in a local git client, and we have not confirmed that
  GitHub applies it when it decides whether a PR has a conflict. A union merge
  can also interleave lines when two entries change the same place. Rejected.
- **Rebuild `CHANGELOG.md` on `main` after every merge.** Under the organization
  rules this needs a bot PR, and an approval, for each merge. Rejected.
- **A third-party tool, such as changie or towncrier.** Each adds an install step
  for every contributor and a fragment format of its own. The command needed
  here is small. Rejected.

## Open questions for Neil

1. **Is the release PR acceptable?** The alternative is to run the command
   right after a release is published, as the backfill in #411 did. That keeps
   the release itself unchanged, but the changelog lags the release by one PR.
2. **Order inside a version.** The proposal orders sections by kind, then by
   date. Ordering by date alone is closer to how the file reads today.
3. **Fragment names.** The proposal uses the branch name. A free-form name is
   also possible, because only uniqueness matters.

## Testing

- Unit tests for the command, against a fixture changelog and fixture fragments:
  - It orders sections by kind, then by date.
  - It refuses a malformed version, a version that is already a heading, and a
    fragment that fails the rules.
  - It deletes the fragments it wrote, and only those.
  - It does nothing when there are no fragments.
  - A second run with the same version refuses.
- A golden test: a known set of fragments produces a known `CHANGELOG.md`.
- A check before the cutover merges: run the command on a copy of the repository
  with the current `## Unreleased` sections moved into fragments. The result
  must hold the same sections as today's file, only reordered by kind.
