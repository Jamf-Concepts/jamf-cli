## CRITICAL: Credential Input Policy

**Never accept credentials (passwords, tokens, client secrets) via CLI flags or stdin.** This prevents exposure in shell history, `ps` output, and CI/CD logs.

- **Human credentials** (username, password): Interactive prompts only (`term.ReadPassword`). No flags, no env vars, no stdin.
- **Machine credentials** (token, client-id, client-secret): Environment variables (`JAMF_*`, `JAMFPROTECT_*`, `JAMFSCHOOL_*`, `JAMFSECURITY_*`) for CI/CD. Interactive prompts for manual use. Config profiles with `keychain:` references for persistent storage. `--token-file` for file-based CI/CD.
- **Never add** `--password`, `--token`, `--client-secret`, `--token-stdin`, or `--client-secret-stdin` flags to any command.
- **Setup commands** (`pro setup`, `protect setup`, `school setup`, `security setup`, `config add-profile`) must always prompt interactively for credentials — no flag or env var bypass.

## CRITICAL: Generated Code Boundary

**Never edit files in `internal/commands/pro/generated/`** — they are overwritten by `make generate`.

**Never edit files in `internal/commands/platform/generated/`** — they are overwritten by `make generate`.

**Never edit files in `internal/commands/security/generated/`** — they are overwritten by `make generate`.

To change generated command behavior, edit the **generator templates**:
- **Modern API commands:** `generator/parser/generator.go` → `resourceTemplate` const
- **Classic API commands:** `generator/classic/generator.go` → `classicResourceTemplate` const
- **Modern registry:** `generator/parser/generator.go` → `registryTemplate` const
- **Classic registry:** `generator/classic/generator.go` → `classicRegistryTemplate` const
- **Jamf Security Cloud commands:** `generator/security/template.go` → `resourceTemplate` const

Templates are Go `const` strings embedded in the generator source — NOT separate `.tmpl` files.

After modifying a template: `make generate && make test`

## Platform Command Contract

Generated platform commands (`internal/commands/platform/generated/`) own **all** CRUD and action operations (list, get, create, update, delete, deploy, undeploy, report, etc.). Hand-written platform commands own **business logic only**: upsert (`apply`), portable export (`export`), profile conversion (`import-profile`), clone, dual-identifier lookup, and operations that orchestrate multiple API calls.

**Rule:** if a new Platform API endpoint maps cleanly to a single HTTP call, it should be a generated command, not hand-written. Wire generated subcommands under the hand-written parent `*cobra.Command`:

```go
for _, sub := range platformgen.NewBlueprintsCmd(cliCtx).Commands() {
    if sub.Name() == "create" { // skip if hand-written apply replaces it
        continue
    }
    cmd.AddCommand(sub)
}
```

CI enforces that `specs/platform/` and `internal/commands/platform/generated/` stay in sync: `make verify-platform-specs`. Run `make sync-platform-specs && make generate` after any spec change.

**Platform specs come from `jamfplatform-go-sdk`'s published `api/` directory.** That is the only place they are normalised and wire-verified against a live tenant, so any other source drifts. Refresh with:

```bash
make sync-platform-specs-from-sdk JAMFPLATFORM_SDK_PATH=/path/to/jamfplatform-go-sdk
```

`specs/platform/` filenames match the SDK's `api/` filenames exactly, so the copy needs no mapping to keep in step. `PLATFORM_SDK_SPECS` in the Makefile is the authoritative set — `sync-platform-specs` copies exactly those and ignores anything else in the drop directory. It is a list rather than a wildcard for two reasons: the SDK's `api/` also holds `pro_api.json`, the Classic documentation and the app-installer specs, which are Jamf Pro APIs generated from this repo's own `specs/*.yaml` and would emit bogus platform commands from Pro paths; and `specs/.platform-source/` is gitignored, so a wildcard made `make verify-platform-specs` depend on whatever a developer last left in a directory that differs per working tree. Adding a platform resource therefore means adding its spec to that list.

This is not housekeeping. A stale copy of the compliance-benchmark spec left `pro rules list` sending `baselineId` after the API renamed it to `baseline-id`; the server ignored the unknown key and answered **0 rules for every baseline**, with a required flag and no error. The test covering it passed the whole time, because it asserted the generator's flag→query plumbing against whatever the stale spec declared rather than the wire contract.

## Architecture

CLI for the Jamf platform. Root command holds shared infrastructure (config, auth, completion). Each Jamf product gets its own namespace — `pro` for Jamf Pro, `protect` for Jamf Protect. Platform API commands live under `pro`.

### Code Generation Pipeline

```
specs/*.yaml ──────────────► generator/parser/   ──► internal/commands/pro/generated/*.go
                               ParseSpec()            + registry.go
                               Generator.Generate()

specs/classic/resources.yaml ► generator/classic/ ──► internal/commands/pro/generated/classic_*.go
                               ParseManifest()        + classic_registry.go

All resources ────────────────► smoke_registry.go (every GET for smoke tests)
                               ► backup_registry.go (list+get pairs for backup/diff)

Entrypoint: generator/main.go
```

Key types in templates: `parser.Resource` (`Name`, `NameSingular`, `GoName`, `Operations`, `IsSingleton`), `parser.Operation` (`Name`, `Method`, `Path`, `IsList`, `IsPaginated`, `IsDestructive`), `classic.ClassicResource`. `IsPaginated` (any GET with `page`/`page-size` params) is broader than `IsList` (list/history only) and gates `--all`/`--limit` auto-pagination so report/action GETs like `patch-report` page through all results.

`ParseSpec` returns `[]*Resource` — most specs produce one, but multi-family specs (e.g. `SelfServiceBranding.yaml`) produce one per family. `IsSingleton` is true for settings-style resources (GET+PUT, no `{id}`) — they get `get` instead of `list`, skip `apply`.

**A resource's name does not tell you which API version it serves, and reading it that way cost the CLI its newest computer inventory endpoint.** Version consolidation happens at two levels: `deduplicateVersionedOps` picks between paths *inside* one spec file, and `DeduplicateVersioned` picks between *resources* across files, keyed on the `-v-{N}s` suffix the parser derives from a file like `ComputersInventoryV3.yaml`. The second one used to treat a resource whose name carries no suffix as the family's legacy base and suppress it outright. That is right for `inventory-preload`, whose base file declares v1; it is wrong for `computers-inventory`, whose base file declares **v1 and v4 together** — so the within-file pass leaves it holding v4, under a name with no suffix, and it lost to the `-v-3s` sibling. Every `pro computers-inventory` command sent `/v3`, and the two v4-only operations (`erase`, `remove-mdm-profile`) were never generated at all.

Nothing failed, which is why it stood: v3 answers on an instance, and the gateway published all four versions. What surfaced it is the gateway's 11.31.0 spec withdrawing v1, v2 and v3 — the version this CLI happened to send became the one refused before a request is sent, and the version it had all along became the only one served. `DeduplicateVersioned` now ranks a family by the version each resource actually serves, read off its operation paths (`resourceAPIVersion`, the highest rank among them), with the name suffix only saying which resources are in the family. `TestDeduplicateVersioned_BaseWinsWhenItServesTheHigherVersion` pins the computers-inventory shape and `..._BaseStillLosesWhenItIsOlder` pins inventory-preload's, because the fix has to not flip the case the old rule was written for.

**Two computers-inventory paths are still version-pinned by hand and do not move with it.** `resourceGetDetailPathOverrides` (`generator/parser/parser.go`) names the detail endpoint `get` uses when `--section` is absent, and `newComputerEraseCmd`/`newComputerRemoveMDMCmd` (`internal/commands/pro_device_actions.go`) assemble their own paths. All three read `/v3` or `/v1` after the ranking fix moved the resource to v4 — a working `get` on a withdrawn detail path, and two destructive commands on withdrawn v1 paths. Grep for a hard-coded version whenever a resource's winning version changes; there is no test that can see a stale literal in an override table.

The v4 arrival also collided head-on: the generated `erase` landed beside the hand-written one, and `pro comp --help` listed the name twice. `pro.go` now `replaceSubcommand`s `erase` and drops the generated `remove-mdm-profile` in favour of the hand-written `remove-mdm` — the hand-written pair target by serial, name or group, confirm the action, honour `--dry-run` and carry the Find My PIN body, where the generated pair take an `<id>`. A duplicate subcommand name is not a choice cobra can make, so a new generated action that shadows a hand-written one has to be resolved in `pro.go`, not left to resolve itself.

See `generator/README.md` for full template reference.

### Generated Command Features

Generated commands automatically get: `apply` (name-based upsert); `get`/`update`/`delete`/`patch` with `--name` (and per-resource `--serial`/`--udid`) for single-`{id}` paths; `patch` with JSON Merge Patch (RFC 7386) + `--set key=value` + shell completion of scalar fields; `--scaffold` on `create`/`update`/`patch` (rendered by `parser.ScaffoldJSON`, shared by all three generators — it skips read-only fields, keeps write-only ones, prefers a spec example over a placeholder, and shows one element inside an array whose element is an object). When a spec declares BOTH a per-`{id}` x-action and a collection-level sibling at the same path minus `{id}` (e.g. `/deployments/{id}/computers/installation-retry` + `/deployments/computers/installation-retry`), `pairCollectionBulkActions` (in `parser.go`, run before name disambiguation) drops the bulk op and records its path on the per-`{id}` op as `BulkActionPath`; the template then adds an `--all` flag that hits the collection-level endpoint in one server-side call instead of the `{id}` one. Each generated Pro and Platform command also carries a `jamf:privileges` annotation (populated from `x-required-privileges` in the spec via `opAnnotations`) surfaced in the `commands -o json` catalog as a `privileges` array; and appended to the 403 hint at runtime by `EnrichPrivilegeError` — in the vocabulary of whichever API served the command (see the 403 vocabulary note under the gateway-coverage section). Classic commands carry no privilege data. All behavior lives in the templates — don't re-document here, read `generator/parser/generator.go`.

**Every classic write takes `--from-file`, not just `apply`.** Classic `create` and `update` read their XML body from `--from-file` or, absent the flag, stdin (`readClassicBody` in `classic_registry.go`; the flag is registered by `classicResourceTemplate`). Stdin alone was unreachable for the callers that most need these commands: AutoPkg's `JamfCLIRunner` passes a body either as `--from-file` or as a `data` dict it serialises to **JSON**, and a JSON body on a `/JSSResource` path is sent with `Content-Type: application/xml` and refused — so a resource with no name-resolution collection (`classic-computer-invitations` and friends, which get no `apply`) had no file-based route at all. The body may hold credentials — an SMTP or LDAP account password — so it belongs in a file, never in a flag value or `argv`.

**Name resolution needs a GET-serving collection.** `apply`, `--name`, `--serial` and `--udid` all work by GETting the resource's collection and RSQL-filtering it, so they are generated only when `nameResolutionPath` (`generator/parser/generator.go`) is non-empty. That is deliberately stricter than `collectionPath`, which answers "what is this resource's collection URL" and to do so falls back to the create-POST path and to the `{id}` path minus its last segment — neither implying the server answers a GET there. Resources whose modern API is POST-collection + GET-`{id}` only (dock-items, venafis, cloud-azure, cloud-ldaps, the PKI settings resources) therefore ship ID-only CRUD: no `--name`, no `apply`. Add a `resourceNameLookupPathOverrides` entry if a sibling endpoint can serve the lookup; that override bypasses the check.

Name-resolution helpers (in `registry.go` / `classic_registry.go`): `readApplyInput`, `extractJSONField`, `resolveNameToIDForApply`, `extractClassicName`, `resolveClassicNameToIDForApply`.

### Runtime Flow

`cmd/jamf-cli/main.go` → `commands.NewRootCmd()` → `PersistentPreRunE` (resolves auth + config, determines product from command hierarchy, builds HTTP client and/or Platform SDK client) → subcommand.

Commands matched by the `chainSkip` set in `root.go` (`completion`, `help`, `version`, `config`, `diff`, `setup`, `multi`, `doctor`, `mcp`, `agent-context`, plus root-level `commands` and any `--scaffold` invocation) bypass auth.

### Auth

Resolution order: env vars (`JAMF_TOKEN`, `JAMF_CLIENT_ID`, `JAMF_CLIENT_SECRET`, `JAMF_TENANT_ID`) > config profile.

Three methods: **token** (pre-existing bearer), **oauth2** (client credentials against instance `/api/oauth/token`), **platform** (client credentials against Jamf Platform Gateway, e.g. `https://{region}.api.jamfcloud.com/auth/token`; requires `--tenant-id` or `--environment-id`; Classic paths routed through `/proclassic/`, modern through `/pro/{version}/`, with the scope in an `X-Tenant-Id` or `X-Environment-Id` header; also constructs `jamfplatform-go-sdk` client enabling Platform API commands).

Secrets in config use prefixed references: `env:VAR`, `file:/path`, `keychain:service/account`. Bare values in `config add-profile` are stored in keychain automatically.

### Jamf Protect Integration

Uses `jamfprotect-go-sdk` (GraphQL, SDK manages tokens/retry/pagination). No use of `internal/auth/` or `internal/client/`. Env vars: `JAMFPROTECT_URL`, `JAMFPROTECT_CLIENT_ID`, `JAMFPROTECT_CLIENT_SECRET` (falls back to `JAMF_*`).

Patterns: positional `<name>` args (not `--name` flag) resolved via `internal/protect/Resolver`. `apply` (upsert from JSON or YAML) instead of separate create/update — output of `export` can be piped to `apply`. List commands flatten to essential fields for table output; `get`/`apply` use `printResult()` (flatten for table/csv/plain, full JSON for json/yaml). Delete and apply-replace require `--yes` or interactive confirm. Granular mutations (`add-analytic`/`remove-analytic`, `add-exception`/`remove-exception`, `add-rule`/`remove-rule`, `add-filter`/`remove-filter`) use read-modify-write and are idempotent.

`plans apply` only sends its cross-resource reference fields (`exceptionSets`, `analyticSets`, `unifiedLoggingFilterSets`, `usbControlSet`) when the input list is non-empty, so omitting or emptying one leaves the plan's existing membership unchanged rather than clearing it — use the granular `remove-*` subcommands to detach. This does **not** apply to a set's own membership list: `ulfs apply` (`filters`) and `analytic-sets apply` (`analytics`) always send the field, so an omitted or empty list clears it.

**`protect restore` is the exception: it clears.** Its contract is that the target ends up matching the document, so an absent membership list has to be *sent* as an empty one — the SDK's `buildPlanVariables` omits a nil list from the GraphQL variables and the server then leaves the field alone, which would let a binding added after the backup survive a rollback. `planExportToInput`'s `clearAbsent` parameter is the switch: restore passes true, `plans apply` passes false. Telemetry needs the SDK's `TelemetryV2Null` rather than an empty value, being a single reference; `usbControlSet` has no explicit-null mechanism in the SDK at all, so a USB control set detached after the backup is the one binding restore cannot converge.

Analytics and ULF additionally support `import --file`/`--dir` matching `jamf/jamfprotect` community repo YAML schema. Both resources' `apply` accepts **either** that community schema or the SDK input shape, sniffed per document (`analyticInputFromDocument`, `ulfInputFromDocument`) — the two disagree on field names (community `actions` are objects vs the input's `analyticActions`; community `predicate` vs the input's `filter`), so decoding one as the other silently produced an empty field and the server refused it. `export | apply` is a documented pipe for both and is covered by tests for both.

`unified-logging-filter-sets` (`ulfs`, SDK v0.8.0+) groups unified logging filters for assignment to plans — the ULF analogue of `analytic-sets`. Sets carry a read-only `plans` back-reference (excluded from `export`, which stays portable by using filter names); filters carry a read-only `sets` back-reference. Attach sets to a plan via `unifiedLoggingFilterSets` in `plans apply`. The server refuses to delete a set that is still used by a plan; deleting a filter cascades it out of any sets.

**Export output shape changed for four resources** (groups, users, api-clients, exception-sets). Cross-resource references now export as **names**, not server IDs: `roles:`/`groups:`/`connection:` in place of `RoleIDs`/`GroupIDs`/`ConnectionID`, and an exception's `analytic:` alongside its `analyticUuid`. Role IDs are small sequential integers, so an ID-shaped document applied to another tenant bound to whatever role held that integer — the wrong grant, silently. Input stays backwards compatible in both directions: `rbacDocumentUsesIDs` routes an ID-shaped document down the old path, exception sets accept a uuid-only exception, and JSON keys that were PascalCase still bind because `encoding/json` matches case-insensitively (yaml.v3 does **not** — it matches the lowercased Go field name exactly, which is why the exception export deliberately carries json tags and no yaml tags except on the one genuinely new field). Anything that *parses* these commands' output needs updating. The reference fields carry no `omitempty`, so `connection: ""` and `roles: []` are written out rather than omitted: an absent list and an empty one mean the same thing to the converters (they always send `[]`), so writing them keeps a document self-describing — which is what lets `apply --scaffold` teach the shape at all — and keeps two tenants' copies of the same group diffable when one holds no roles.

`protect analytics overrides` manages the **tenant overlay on Jamf-managed analytics**. Jamf publishes analytics centrally: `analytics list` in a stock tenant returns ~156 rows all flagged `jamf: true`, and the server refuses `updateAnalytic` against any of them (`"This mutation may only be used for custom analytics"`). What a tenant *can* change is `tenantSeverity` and `tenantActions`, written by the separate `updateInternalAnalytic` mutation (`UpdateInternalAnalytic` in the SDK, served on `/app`). Since the definitions are identical in every tenant, that overlay is the only part of a Jamf-managed analytic worth capturing — so `overrides export` emits it keyed by analytic **name** and `overrides apply` replays it into another tenant, skipping entries that are absent or custom. `overrides apply` treats an absent half as "no override" and clears it, which is what makes re-applying the same document idempotent; use `overrides set` for partial edits, where an omitted flag leaves that half untouched. Both `overrides apply` and the `analytic-overrides` restore closure report a refused entry and continue, then fail at the end with both counts — aborting at the first failure left the earlier entries written and unreported and the rest never attempted, which made a retry impossible to reason about.

Two traps this exposes. `analytics list` reports Jamf's **baseline** severity, not the effective one, so an analytic overridden to `Low` still displays as `High` — `overrides list` shows baseline, tenant and effective side by side. And `analytics export` emits only the community YAML definition, dropping `tenantSeverity`/`tenantActions` entirely, so it silently discards exactly the customisation a customer made. `Analytic.hash` is a revision stamp, not a content hash — it changes across a mutate-and-revert cycle that leaves content identical, so it cannot be used as a change-detection or cross-tenant identity key.

`protect backup` and `protect restore` capture and replay a whole tenant. Backup writes each object to its own file under a per-resource directory in the same portable form the matching `export` produces; restore walks that directory in dependency order, resolving every reference by name against the target as it goes. Both take `--resources` (allowlist) and `--exclude` (denylist), which compose and both shell-complete; restore adds `--include-defaults` and reads the root `-n, --dry-run`. `protectResourceListHelp` renders the vocabulary into each command's `--help` from the table itself — hand-writing it would drift, and before that the only ways to discover a resource name were completion and reading the error from a wrong value. Backup exits non-zero when any resource failed — matching `pro backup`, because a backup that exits 0 with a resource missing is indistinguishable from a good one to the job that scheduled it — with `--allow-partial-failure` to downgrade. Backup prunes documents an earlier run left that no longer match the tenant, reporting each — without it a backup directory is the union of every run that wrote to it, and since restore applies whatever it finds, a deleted object gets silently recreated (switching `--format` had the same effect, leaving both extensions on disk for restore to apply twice). `pro backup` does **not** prune; the divergence is deliberate, because Pro has no restore so a stale file there only misleads a diff. `protectPruneStale` only ever considers files this command could have written — inside a directory named after one of its own resources, or the single file a singleton owns, and only with an extension restore reads — and never prunes a resource whose export failed, since the true object set is unknown. `--no-prune` keeps them. **Pruning is refused when the directory's `_meta` records another tenant having written to it**, because it is keyed on "the object set of the tenant being backed up right now": pointed at another tenant's backup it would delete that tenant's documents for every object this one lacks, reported only as a prune count, with no `jamf:destructive` annotation and no confirmation. That record is **cumulative and written first**, which is what makes the guard trustworthy: `TenantURL` alone was last-writer-wins, so a `--no-prune` run — the very thing the refusal recommends — relabelled the directory and the *next* run by that tenant pruned the first tenant's documents; and writing `_meta` last left an interrupted run's documents with no provenance for the next run to refuse on. Each run appends its own normalised URL to `Tenants` (the comparison folds case and a trailing slash, since `resolveProtectClient` takes the URL verbatim from four sources), claims the directory before exporting anything, and replaces the manifest with counts at the end, removing any copy an earlier `--format` left in the other extension so one manifest is authoritative. A `_meta` that is present but unparseable beside documents **refuses the run outright**, `--no-prune` included: rewriting a manifest it could not read would drop another tenant's claim and hand the next run a guard that passes. A manifest that is **absent, zero-length, or parses to no tenant** beside documents refuses the *prune* — not the run — for the same reason one run later: both used to read as "fresh directory" and permit it, and a zero-length file is exactly what an interrupted or out-of-space write leaves, so the state the write-the-claim-first ordering exists to survive landed in the one branch the guard did not cover, looking clean rather than broken. That case is a pruning question rather than a provenance-rewrite one — there is no claim to overwrite and lose — so `--no-prune` is a real way forward there and the refusal says so: it records the tenant, and the run after it prunes normally. The root `-n, --dry-run` covers the prune and nothing else: documents are still written (that is what `--output` asked for, and `pro backup -n` writes its files too), and every removal the run would have made is reported `[dry-run]`. Gating the `protectPruneStale` *call* instead of its `os.Remove` would delete nothing and report nothing, which reads as "there was nothing to prune"; the claim manifest also carries the previous run's `Resources`/`Counts` forward rather than blanking them, so an interrupted run degrades to a stale inventory instead of describing a backup that never happened. Restore reports a mixed result the same way backup does — `exitcode.PartialFailure` (7) rather than `General` (1), downgradable with the same `--allow-partial-failure` — so one job can observe both halves of a round trip identically. Both commands read the extension set from `protectRestoreExts`, so what backup prunes is exactly what restore applies; accepting only `.yaml`/`.json` for singletons made a hand-written `insights.yml` a file backup deleted and restore ignored. Object names are free text and `protectFileNameSafe` is lossy in both directions (runs of illegal characters collapse; a case-insensitive filesystem folds case), so `protectNameAllocator` appends a name-derived discriminator on collision rather than letting one object overwrite another while the count still reports two. Restore updates what exists and creates what does not — it never deletes, so an object in the tenant but absent from the backup survives. Per-object granularity is the filesystem: delete files from the backup directory to skip them (which is how you restore synthetic users while holding back real ones).

Insights and identity provider connections are captured as state documents rather than objects: the insight catalogue is Jamf-published so only the enabled/disabled split is a tenant's own data, and connections have no create API at all, so they are recorded for reference (a user or group naming one restores only where that name exists) and never replayed.

`protectResources()` in `protect_backup.go` owns the set, and its `Order` field is the correctness argument — members before the sets naming them, sets before the plans binding them, roles before groups before users. A test asserts that chain rather than the numbers. Deliberately not replayed: Jamf-managed content, tenant defaults (`protectDefaultObjects`), API clients (a new secret is issued on create), and data forwarding (its response is not its update shape and its `cloudformation` blob embeds a tenant-specific IAM ExternalId).

Wire facts established by cloning between two live tenants, none of which are guessable from the specs:

- **Jamf-published analytic UUIDs are stable across tenants** — `BlazingKeylogger` is `da360eb3-…` in both. Custom analytics get per-tenant UUIDs. An exception set therefore exports its target analytic by **name** (`analytic:`) as well as uuid, and apply rebinds the name against the target; the uuid alone was portable only for Jamf analytics. **A foreign `analyticUuid` is rejected, not silently accepted** — the server answers `createExceptionSet: Action blocked due to dependencies on this resource.`, which names neither the analytic nor the uuid nor the reason. Established by applying two documents differing only in that uuid. `exception-sets` therefore sits at `Order` 20, not alongside the analytics: the name only resolves once the analytic exists in the target.
- **Identity provider connection names are tenant-specific** (`jamf-id-db` exists in both, but `jamfmspservices-protect-jamfcloud-com` only in one), so a user or group naming a connection restores only where that name also exists.
- **RBAC reference lists must marshal as `[]`, never `null`** — a user in groups but holding no direct role otherwise fails with `input → roleIds: None is not of type 'array'`.
- **A plan's `customEngineConfig` has PascalCase JSON keys and all-lowercase YAML keys** (`MalwareRiskware` vs `malwareriskware`) because `CustomEngineConfigInput` carries json tags and no yaml tags. Modes are `PREVENT`/`REPORT`/`DISABLED`. Backup and restore are self-consistent; only a hand-written document trips on it. `plans apply` also *requires* `actionConfig` — omitting it answers `actionConfigs: contains invalid characters`, because the SDK sends the field regardless.
- **Action config `params` is `AWSJSON!`**: read back as an object, but the input wants a JSON-encoded *string*, and it cannot be omitted. The response also fills every member of the `ReportClientParams` union with zero values, and `batchConfig.sizeInBytes` returns 0 against a documented minimum of 1000. The union's `HttpClientParams` selects `headers { header value }` in full, so an HTTP report client's bearer token or API key is captured verbatim and cannot be redacted without breaking restore — `action-configs` and `data-forwarding` therefore carry a `SensitiveReason`, are written `0600` rather than `0644`, and are reported before the operator commits the tree. The mode needs an explicit `os.Chmod` after the write: `os.WriteFile` passes `perm` to `OpenFile(O_CREATE|O_TRUNC)`, which applies it *only when the file is created*, and git records no non-exec permissions — so a clone of a backup repo hands every file back `0644` and a re-run would have kept it there while still reporting `0600`. The legacy `ForwardSentinel.sharedKey` *is* redacted, since data forwarding is never replayed. (`ForwardSentinelV2` got this right and reports `secretExists` instead.)
- **USB control vendor and product IDs need a `0x` prefix** (`0x0781`); bare hex is rejected as "contains invalid characters".
- **`commsConfig` is always sent** by the SDK, so `protocol` must be one of `mqtt`/`wss/mqtt`/`auto`; its `fqdn` is the region-assigned IoT endpoint and the target keeps its own. That and an exception's rebound `analyticuuid` are the only two fields that legitimately differ after a clone — for the latter, equality would mean the rebinding *failed*. Verified cross-tenant on `0cf1041`: 26 documents applied, 0 failed, re-run idempotent, 24 of 32 files byte-identical and all 8 differences accounted for.
- **Data retention updates are rate-limited to once per 24 hours**, which is why `data-retention` restore compares `dataRetentionToInput(current)` against the document and writes only a real change — an unconditional write made every re-run inside that window report a failure for a resource already in the desired state.
- **Writing a setting the tenant already holds can be refused.** Disabling a change freeze that is not on answers "Tenant '...' is not in a change freeze", so `config-freeze` and `insights` compare before writing and only send real changes. `data-retention` does the same for the rate limit above. **`accessGroup: true` on a connection-less local group is the sharpest case**: `createGroup` accepts it and stores `true`, but `updateGroup` refuses it *even when `true` is already the stored value* — so a restore succeeded once and failed on every re-run. It can be turned off via update and never back on. `protectGroupUpdateSatisfied` therefore skips the update when the target already holds the desired state, and when it does not, says the operation is create-only rather than passing through the server's bare message. It is shared by `restoreGroup` and `groups apply`, because the asymmetry is a property of the API rather than of restore — `groups export | groups apply` hit it too. **"Skips the update" has to mean "there was nothing to send", not "the flag matches"**: the first version of the guard returned satisfied on `accessGroup` alone, so a document that also added a role printed `nothing to update` and exited 0 with the role grant silently dropped — a worse failure than the raw server error it replaced. `groupUpdateWouldChange` compares every field `updateGroup`'s mutation can carry (name, accessGroup, roleIds — sorted, since the server returns roles in its own order) plus the connection it cannot, and a non-empty diff is an error naming the fields that could not be applied.
- **Telemetry `events` is `[String]!` in the schema but validated against an undeclared server-side list** — a wrong value answers "This mutation may only use predefined types". `network_connect` is valid; `network`, `network_listen`, `network_accept`, `dns_request`, `process_exec` and `file_create` are all rejected, so the list is narrow and does not follow the `GP*Event` naming used by analytic `inputType`.

`protect downloads` subcommands fetch installer/uninstaller/pppc-profile/tamper-prevention-profile/root-ca/csr/websocket-auth/summary files. `protect plans config-profile <name>` downloads a `.mobileconfig` (use `--no-*` to exclude payloads, `--sign` to sign).

### Jamf Platform API Integration

Uses `jamfplatform-go-sdk` (REST, SDK manages tokens/retry/pagination). Platform commands live under `pro` and appear in "Platform:" help group — the exceptions are **AI Governance, Jamf Account and audit, which live under `platform`** because they are not Jamf Pro surfaces at all (see their sections below). A single `auth-method: platform` profile enables both Pro API (routed through gateway) and Platform API (via SDK).

Runtime-gated: commands are always registered but `RunE` starts with `requirePlatformClient(cliCtx)` and errors with setup instructions when platform auth not configured.

Name resolution via `internal/platform/Resolver` (blueprints by name, benchmarks by title, baselines by title, device groups by name). Devices use SDK filter methods directly (UUID vs serial auto-detected by hyphen presence).

CRUD pattern: `apply` (upsert, blueprint uses merge-patch; benchmark is create-only — SDK has no update), `get`, `delete`, `export`. `apply --scaffold` prints create request template (auth skipped for scaffold).

**Identifier convention differs from Protect.** Protect takes a positional `<name>`; Platform takes a positional **`<id>`** plus a `--name` flag (`delete <uuid>` or `delete --name "My Blueprint"` — passing a name positionally is sent as an ID and 404s). This holds for both the generated commands (template: `generator/platform/template.go`, gated on `SupportsNameLookup`) and the hand-written ones (`resolveBlueprintID` in `pro_blueprints.go`), which reject `<id>` and `--name` together. Exceptions: `blueprints clone <source-name> <new-name>` takes names positionally; `blueprints import-profile [<id>]` sniffs its positional (`isClassicID` in `pro_blueprints.go`) — an all-digit argument is a Classic ID, anything else a display name — to keep pre-#316 name-based invocations working. Consequence: a profile whose display name is all digits must be looked up with `--name`. Do not copy the sniffing into new commands without a comparable compat reason.

Naming: `platform-` prefix where overlap with existing Pro resources (`platform-devices`, `platform-device-groups`); no prefix for unique resources (`blueprints`, `compliance-benchmarks`, `ddm-reports`).

Commands: `blueprints` (`bp`) — CRUD, deploy/undeploy, clone, scope, components, import-profile (auto DDM conversion), report. `compliance-benchmarks` (`cb`) — benchmark CRUD (apply/get/list/clone/delete/export; create-only, no update). `baselines`/`rules` — read-only mSCP reference data (list). `benchmark-reports` — compliance reporting (`rules`/`devices`/`compliance-percentage`, keyed by benchmark ID). `platform-devices` (`pdev`), `platform-device-groups` (`pdg`), `ddm-reports` (`ddm`).

**`ddm-reports declaration get` and `device get` are gone as of the v1942 declaration-reporting spec.** Both were deprecated in favour of a sibling on the same resource that the CLI already shipped — `GET /v1/declarations/{id}` → `.../devices`, `GET /v1/devices/{id}` → `.../declarations` — so the capability survives under `declaration devices` and `device declarations`. The one difference that matters: **both successors declare `filter` required** where the deprecated pair did not, so there is no longer an unfiltered read. `ddmAllDeclarationsFilter` (`internal/commands/pro_ddm_reports.go`) is the tautology that stands in for one, `active=in=(true,false)`, and the hand-written commands (`pro device`, `pro report`, `pro audit`) were already using the filtered successors, so nothing hand-written broke. A CLI user needs `--filter 'active=in=(true,false)'`.

### Jamf Security Cloud Integration

Uses a hand-rolled client (`internal/security`) — no product Go SDK exists. Auth is a Basic-login-for-JWT exchange (`POST /v1/login` with `base64(clientId:clientSecret)` → a 15-minute JWT), not OAuth2 client-credentials. Critically, each of the three APIs — Risk, Device Lifecycle, and Shared Signals & Events (SSE) — is provisioned as its own "Security Integration" in the Radar portal with its own application ID/secret, and the resulting JWT is scoped to exactly one API via its `aud` claim. So `internal/security.Client` tracks three independent credential pairs and token caches (`DoExpectRisk`/`DoExpectLifecycle`/`DoExpectSSE`); any subset may be configured, and commands for an unconfigured API fail with a "run security setup" hint rather than the whole product refusing to start.

Risk and Device Lifecycle share one host (`api.wandera.com`, which also serves `/v1/login`); SSE lives on `sse.jamf.com` per its own OpenID SSE framework discovery document. Unlike Pro/Protect/School, there's no per-tenant URL — tenancy is carried inside the JWT's `customer_id` claim, so `security setup` never prompts for a URL (env/profile overrides exist for `--url`/`JAMFSECURITY_URL`/`JAMFSECURITY_SSE_URL` in case Jamf ever stands up regional or sandbox hosts).

Commands are **generator-owned**, same as Platform — the eleven total operations across the three specs are hand-mapped (not tag/family auto-detected like Platform's parser) because they span wildly different shapes (a paginated list, singleton-style get/update/delete, bulk actions with no `{id}` in their path at all) that are too few and too irregular to benefit from generic detection. See `generator/parser/security.go`'s `securityOpsByFile` map. Commands: `risk` (`list`/`override`), `device-lifecycle` (`purge` — destructive, `{customerId}` filled at request time from the Device Lifecycle JWT, never user-facing), `stream` (SSE singleton-style get/update/delete), `status` (get/update), `verification` (`trigger`), `jwks`/`well-known` (SSE discovery, read-only). No name-to-ID resolution — every identifier (guid/externalId) is supplied directly.


#### The gateway-served half of Security Cloud

Part of Jamf Security Cloud is served on the **platform gateway** (`/securitycloud/...`) rather than on `api.wandera.com`, and is reached with platform client-credentials plus a Security Cloud tenant ID — not the scoped Basic-login pairs above. Five specs, 47 operations: DNS (`dns-zones`, `dns-search-domains`, `dns-custom-hostname-mappings`), ZTNA (`ztna-apps`, `ztna-gateways`, `ztna-grouped-gateways`, plus read-only `ztna-shared-gateways` / `ztna-predefined-apps`), `content-categories`, `device-groups`, and UEM Connect (`uem-connectors`, `uem-connector-enablement`, `uem-sync-settings`, `uem-sync`, `uem-activation-profiles`).

These are generated by the **Platform** generator (`generator/platform/`) into `internal/commands/platform/generated/`, then wired under `security` in `security.go` — the same namespace as the Wandera-served commands, because it is one product to whoever is typing, and `pro` already mixes two auth paths under one namespace.

Because the two halves take **different credentials**, every command says which API serves it. The `Short` carries it in words — `(Security Cloud · platform gateway)` vs `(Security Cloud · Radar API)` — which is what `security <TAB>` shows, since Cobra uses `Short` as the shell-completion description. The `jamf:api` annotation (`platform-gateway` / `radar`) carries the same fact for machines and surfaces in the `commands` catalog as `api`. Both come from the generators, so a new resource gets them without a CLI edit; `TestSecurityCommandsDeclareTheirAPI` fails if one is emitted without the other. `security setup` declares neither — it writes credentials and calls no API.

**Specs are sourced from the SDK, not from `public-apis-oas`.** Drop `jamfplatform-go-sdk`'s published `api/securitycloud_*.json` into `specs/.platform-source/`, then `make sync-platform-specs`. The upstream `-beta` specs are wrong in ways only wire probing revealed, and the corrections live in the SDK's `tools/generate/config.json`, validated by acceptance tests against a live tenant. The SDK publishes them as OpenAPI extensions that this generator reads, so no override table is duplicated here — `specs/platform/` is currently a mixed drop: the three `account_*.json` specs and `audit_api.json` are **v1671** and unchanged since, `ai_governance_policies_api.json` is **v1877**, `device_inventory_api.json` and `device_management_action_api.json` are **GitOps build v1839**, `securitycloud_device_groups_api.json` is **v1865**, `securitycloud_uem_connect_api.json` is **v1981 plus one SDK wire patch** (the response-side `deviceSyncAuth`; the request-side patches this file used to list are upstream's own as of v1882 — see the discriminated-union note below), `declaration_reporting_service.json` is **v1942**, the other three Platform specs (blueprints, compliance-benchmarks, device-groups inventory) are **v1807**, and `securitycloud_ztna_api.json`, categories and dns are **v1981** — the build that first published all four Security Cloud specs to `external/`, so they no longer carry a stage server URL, an "(STAGE)" title or a `us1` region default. That promotion is inert to the generated commands (`servers[0].url`'s *path* is all `serviceSegment` reads, and it is `/securitycloud` either way), but it does mean the mixed `/api`-prefixed and bare URL shapes `TestServiceSegment` pins are now both live in one drop for a second reason. The two coverage specs are separate again: `pro_api.json` is **v1942** (666 operations, down 122 — see the withdrawal note under gateway coverage) and `classic_api_resource_documentation.json` is unchanged, the SDK having held it at v1897 rather than take v1942's 20 Classic withdrawals — **a permanent hold, not a provisional one**, on a structural argument rather than a probe. Classic `POST /patchsoftwaretitles/id/0` is the only call that mints a `softwareTitleId`, which the Pro v3 patch-configuration endpoints require on create, and the obvious substitute cannot supply one: of the 1552 `name_id` values in Jamf's source catalogue, 916 are non-numeric hex-ish definition keys (`0F5`, `2DE`, `41D`) while `softwareTitleId` must be a positive numeric string per the server's own `INVALID_ID` message, and the 636 all-digit ones are rejected anyway with `400 SOFTWARE_TITLE_ID_NOT_FOUND`. `name_id` names what to subscribe to; `softwareTitleId` names a subscription. So taking the Classic withdrawal would make patch software titles unseedable end to end, with no path back. The mix is expected — the SDK re-ingests per family, and a family whose spec is byte-identical is not bumped for the sake of a version number:

- `x-jamf-tenant-path-version` (spec root) — the URL version segment a spec's paths need but omit. The versionless form answers **403 `BAD_PERMISSIONS`**. **No spec sets it any more**: categories moved the version into its own paths in build v1353, dns and ztna followed in v1416, and build v1495 then dropped the tenant segment entirely in favour of the `X-Tenant-Id` header. The support stays because the next spec to arrive without a version prefix needs it — `normalisePlatformPaths` still consumes it — but it no longer has anything to do with tenancy. A spec that gains the prefix while *keeping* the extension would send `/v1/v1/…`, so check the paths rather than the extension when a spec is bumped.
- `x-jamf-expected-status` (operation) — the success status the server really answers (`PUT .../groups/{id}` → 200, not the declared 204).

Extensions rather than corrected paths because the SDK's `api/` doubles as its own generation fallback, keyed on the source spec's paths.

**Build v1671 flipped the Platform privilege vocabulary, and one entry is an authorization change rather than a rename.** `read:pro:blueprints` became `blueprints:read`, `create:pro:device-groups` became `device-groups:create`, and the `read:pro:X` / `read:school:X` alternates collapsed to a single name — the same flip Security Cloud took in v1559, now applied to all six Platform families. No longer cosmetic in the CLI: as of the 403-vocabulary work these names are what a platform 403 prints, rendered through `internal/privileges` into the section and permission name Jamf Account's picker shows, as well as surfacing in the `commands -o json` catalog. The exception is **`erase` and `unmanage`, which moved to `destructive-device-actions:execute`**, split out of `device-actions:execute` — so `pro platform-devices erase` and `unmanage` can now 403 on a credential that executes every other device action. Build **v1839 moved `DELETE /v1/devices/{id}` onto that same scope**, from `devices:delete`, which no longer exists anywhere in the specs: `pro platform-devices delete` is now grouped with the two destructive actions rather than with the read and update it sits beside. This is the half of the v1824 privilege reformat the SDK took, being separable from that build's operation withdrawals and confirmed verbatim by the GA docs draft.

**The GA base URL is `https://{region}.api.jamfcloud.com`, and the `/api` segment is gone.** This is the breaking change of the 2026-09-01 Platform API GA, and it moved every gateway path in this repo. The GA gateway mounts each namespace at the root: `/blueprints/v1/blueprints` serves, `/api/blueprints/v1/blueprints` answers **`404 page not found`** — Tyk's unrouted response, not the gateway's `{httpStatus, traceId, errors}` envelope. Wire-checked here 2026-08-28 against EU on one credential in one run: `/blueprints/v1/blueprints`, `/devices/v1/devices`, `/device-groups/v1/device-groups`, `/compliance-benchmarks/v1/benchmarks`, `/pro/v1/categories` and `/proclassic/categories` all answered 200 while every one of their `/api/…` forms answered 404. `/auth/token` is at the root on both hosts and tokens are portable between them.

The pre-GA host `{region}.apigw.jamf.com` is retired and required the segment the new host does not serve, so it is a **hard swap, not a per-host selection** — the same call the SDK made (`b354d78`), and the same reasoning as the tenant path→header migration below: a second code path nothing exercises is how the earlier URL-shape bug survived weeks. Four things moved together:

- `serviceSegment` (`generator/parser/platform.go`) now reads the namespace off `servers[0].url`'s **path** instead of cutting the URL on `/api/`. That marker does not appear in `{region}.api.jamfcloud.com` — the host's `api` is dot-delimited — so the old implementation returned `""` for every v1807 spec, and an empty service silently drops the namespace from every generated path. No error, no warning, every command 404s. `TestServiceSegment` pins both URL shapes, because one spec drop legitimately mixes them: the six Platform specs are v1807 and carry no `/api`, while the five Security Cloud ones are generated from a different upstream tree that still declares it.
- `normalisePlatformPaths` prefixes `/{service}` rather than `/api/{service}`.
- `rewritePathForGateway` (`internal/client/client.go`) maps `/api/v1/x` → `/pro/v1/x` and `/JSSResource/x` → `/proclassic/x`. Note the `/api` a caller-facing path carries is the *instance's*, added by `Do`; the gateway rewrite replaces that segment rather than prefixing onto it.
- `pdgListPath` (`internal/commands/pro_platform_device_groups.go`), the one hand-written platform path builder.

`platformGatewayRegions` (`internal/commands/platform.go`) holds the GA hosts, and `platformGatewayURLForRegion` refuses a profile still naming the retired one, from `ResolveAuthForProfile`, before any request is sent. That refusal exists because the wire symptom is useless: the failure lands in the **token exchange**, before the command the user typed is sent, and the answer is an edge-level 403 with an HTML body naming neither the host nor the reason. Rewriting silently was the other option and is worse — the profile on disk stays wrong for every other tool reading it, and a URL the user did not type is a bad thing to send a credential to. So it names the replacement and the user edits the profile.

**Verified end to end through the CLI on the GA host, 2026-08-28** (EU tenant, env-var platform auth, one run): Pro modern (`pro categories list` → `GET https://eu.api.jamfcloud.com/pro/v1/categories`, confirmed in `-vv`), Classic (`pro classic-allowed-file-extensions list`), Platform (`pro blueprints list`, `pro platform-devices list`, `pro compliance-benchmarks list`), the multi-segment `/ddm/report/v1` namespace (`pro ddm-reports device get <id>`), the hand-written `pdgListPath` builder via `pro platform-device-groups get --name`, and the device-actions dry-run preview (`[dry-run] POST /device-actions/v1/devices/{id}/restart`). `pro baselines list` and `pro rules list --baseline-id cis_lvl1` were run as the stale-spec canary this file warns about: the request went out as `GET /compliance-benchmarks/v1/rules?baseline-id=cis_lvl1` with the kebab-case param and returned **110 rules, not 0**. (Baseline IDs are slugs — `cis_lvl1` — so `--baseline-id 1` is a 404, not an empty answer.) Security Cloud answers `403 BAD_PERMISSIONS` on `/securitycloud/v1/categories` for this tenant, which is the entitlement answer, not a routing one. The same read battery passed on a **US** tenant against `https://us.api.jamfcloud.com`. Uploads were deliberately not exercised — see the `.pkg` blocker below.

The full `make smoke` GET sweep was then run **twice, once through the GA gateway and once against a direct Jamf Pro instance**, as a control: **58 failures either way**, with identical class counts (52 "response is not valid JSON", ~150 "no ID available"). Those are pre-existing smoke-test design issues — the suite asserts JSON on endpoints that legitimately return XML, CSV, a certificate, a script or a p12, and most of the rest need seeded IDs — so the identical count across two hosts and two tenants is what shows the `/api` drop introduced no regression anywhere in the sweep. Two fixes came out of running it: `smokeClient` never enabled gateway mode, so the suite was structurally blind to the shape that had just changed (every request went out instance-shaped and 404'd); and `make smoke` ran `-run 'TestSmoke'`, which also matches `TestSmoke_Seed` and therefore **created objects on the tenant it was asked to inspect** — now `-run 'TestSmoke_Tier'`. Seeding is `make smoke-seed`, explicitly.

`make smoke` is also how the Classic-write WAF block below was found: 13 of 13 Classic creates were refused while both modern JSON creates succeeded.

**Tyk did not move, and that is what keeps audit coverage intact.** Prod's api-definitions still declare `listen_path: /api/{namespace}` and none declares a bare `/{namespace}` (checked at `origin/master` 2026-08-28), so the new CloudFront edge is prefixing `/api` ahead of the gateway. That is also the only reading consistent with every namespace returning byte-identical statuses on the new host, pre-existing failures included — the same gateway behind a different edge, not a re-implementation. `scripts/audit-coverage.py` therefore adds `EDGE_PREFIX` back on before matching; without it the script reports all 45 mutations as unrouted, a false alarm about the loudest possible failure. If Tyk later gains bare `/{namespace}` listen paths, set that constant to `""` — the answer has to come from the deployed definitions, not from the constant.

**App installers are not reachable through the platform gateway — Jamf Pro direct only.** `pro app-installer-titles`, `app-installer-deployments` and `app-installer-global-settings` are generated from `specs/AppInstaller*.yaml` like any other Pro resource, so in gateway mode they are sent to `/pro/v1/app-installers/...` — which the gateway does not expose. The surface was always a reverse-engineered one with no published spec (the SDK dropped it outright in `7ed7af2`), and it stays instance-only.

Nothing in this repo can route around that, so the handling is to make the failure name the fix — and since app installers are wire-probed rather than merely undocumented, the command is now **refused before a request is sent** rather than only annotated on failure. Both halves are covered in the gateway-coverage section below; `gatewayUnservedNote` (`internal/client/client.go`) is the response-side half, still appended rather than substituted and still gated on the body carrying `BAD_PERMISSIONS` or `404 page not found`, because both statuses can legitimately mean what they normally mean (a deployment ID that really is gone answers Jamf Pro's own JSON 404 through the gateway). `TestGatewayUnservedNote` pins every direction.

#### Which Pro and Classic endpoints the gateway actually carries

**The gateway's published Pro/Classic API is the contract, and its current route set is wider than that contract on purpose.** Some endpoints absent from the published surface answer today; they are routed transitionally and are expected to stop. So a command outside the published surface is **refused on a gateway profile before a request is sent**, precisely *because* it may still work — every day a workflow keeps running against a route that is going away, the eventual failure gets more expensive, and it arrives as a bare `403 BAD_PERMISSIONS` with nothing saying a withdrawal caused it. Full reasoning, including the two wrong designs that came first, in `docs/solutions/logic-errors/gateway-spec-absence-is-not-unrouted-2026-08-31.md`.

The coverage manifest is `specs/gateway/coverage.json`, committed, derived from **jamfplatform-go-sdk's published `api/`** — the same source as `specs/platform/`:

| spec | what it is |
|---|---|
| `pro_api.json` | the Jamf Pro API as published **on the gateway** (451 paths, 666 ops, 11.31.0) |
| `classic_api_resource_documentation.json` | the Classic API, likewise (273 paths, 606 ops, 11.28.0) |

Both are listed as `PLATFORM_SDK_COVERAGE_SPECS` in the Makefile and **must never join `PLATFORM_SDK_SPECS`**: they describe Jamf Pro APIs this repo already generates from `specs/*.yaml`, so handing them to the platform generator emits a second set of Pro commands built from gateway paths. `make sync-platform-specs-from-sdk` copies them into the drop directory and re-derives the manifest, so one SDK sync refreshes everything; `make sync-gateway-coverage-from-sdk` does the coverage half alone.

The manifest records the SDK revision it came from, and two things about that were wrong on the first attempt in ways worth not repeating. **`cd '' && git rev-parse` succeeds** — an empty `JAMFPLATFORM_SDK_PATH` leaves the shell in this repo, so the obvious one-liner stamped *jamfpro-cli's own* commit into the manifest as the SDK's; the path is now tested with `[ -d .../.git ]` before `git -C` is used, because provenance that is confidently wrong is worse than provenance that admits it does not know. And **`gateway.CarryForwardProvenance` keeps a recorded revision** a later run was not told: re-deriving from the same unchanged specs must not blank it, or `verify-gateway-coverage` reports a stale manifest byte-identical apart from the field it just erased. Same reasoning as the Protect backup `_meta` manifest carrying the previous run's inventory forward.

**Two things had to become true before the SDK could be the source, and both now are (SDK `adb8d7b`).** Its build used to *strip* 24 paths the gateway declares — inventory-preload v1, the team-viewer preview family, `cache-settings`, `settings/obj/policyProperties` and others — which would have refused two dozen commands the published surface carries; `adb8d7b` whitelisted the remaining 38 jpapi paths and the published spec is now method-for-method identical to the gateway's own drop. And coverage needs the **gateway scope** per operation, which only the GitOps bundle's `_permissions/routes.yaml` used to carry; the SDK's `x-required-privileges` now reproduces it exactly — checked at 1352 operations across both specs, zero disagreements, none on either side alone. So the bundle route is **deleted, not kept as a fallback**: a second code path nothing exercises is how the earlier URL-shape bug survived weeks.

This does not change where `specs/platform/` comes from — the SDK was always canonical there — and it is worth knowing why the bundle could never have replaced it: the production bundle carries no `jsc-dns`, `jsc-ztna`, `jsc-categories` or `uem-connect` at all (stage/dev only), and the SDK's `uem-connect` copy holds a 19th schema its own wire patches restore, which is what makes `uem-connectors create --scaffold` correct.

`generator/gateway` reads the manifest, stamps every Pro and Classic operation with a `jamf:gateway` annotation, and emits the runtime table `internal/gateway/coverage_gen.go`. **One level, `unserved`, and every entry refuses.** What varies is `jamf:gateway-basis`, which selects the wording only:

- **`probe`** — a recorded, corroborated wire probe found it unrouted. The message states the fact. One entry: `/pro/v1/app-installers` (17 operations).
- **`unpublished`** — absent from the published spec. The message says the endpoint may still answer today, that this is transitional, and that it is refused now rather than later. 36 operations: `api-roles`, `api-integrations`, `api-roles-privileges`, the `auth`/`oauth` families, `environment-type`, `oauth2/session-tokens`, `system/initialize-database-connection`, `POST /v2/mdm/commands`, `classic-computer-configs`, `POST /v1/system/initialize` and `POST /v1/system/platform-initialize` (the v1897 ingest), and — as of v1942 — `/pro/v2/computer-groups/static-groups` (5) plus `POST /pro/v1/computer-inventory/{id}/{erase,remove-mdm-profile}` (2).

**v1942 withdrew 122 Pro operations, and it is a superseded-version purge rather than a capability loss: every one has a published higher-version successor.** That is what makes it safe to follow, and it is worth checking rather than assuming on the next drop — the check is one script over the manifest, matching each withdrawn path's version-stripped tail against the surviving keys. The four families are `computers-inventory` (v1, v2 and v3 gone, **v4** published), `computer-groups` smart and static (v1 and v2 gone, v3 published), `mobile-device-prestages` (v2 gone, v3 published), `inventory-preload` (unversioned and v1 gone, v2 published), plus `patch-software-title-configurations` v2 and `mobile-device-groups` v1. Nothing new appeared; no surviving path lost a method.

**One of the surviving versions narrowed what it accepts, which a coverage manifest cannot show.** `pro computer-inventory-collection-settings custom-path` sends v2, and this repo's own specs already say why that matters: `CreatePath.scope` is `[APP, FONT, PLUGIN]` on v1 while `CreatePathV2.scope` is `[APP]` alone. Wire-checked 2026-09-01 — v1 served all three and v2 accepted only `APP`, case-sensitively, on the same instance minutes apart — so it is a real v2 restriction rather than a publish artefact, and its 400 is field-attributed and leaks the Java DTO class name. The Pro generator renders no "Allowed values:" lines (only the platform one does), so nothing in `--help` says so; a caller asking v2 for a FONT or PLUGIN path gets a 400 for a value v1 accepted. Worth knowing generally: a version withdrawal is a version *replacement*, and the successor is not always a superset.

So the withdrawal is not what the CLI had to be protected from — it is what **exposed** where the CLI was already sending the wrong version. See the version-ranking note below; the seven refusals left over are the two deprecated command names that survived it, each with a live sibling already shipped: `pro static-computer-groups` (v2) beside `pro computer-groups-static-groups` (v3), and the standalone `erase-device-computers`/`remove-computer-mdm-profiles` resources, which `pro.go` already suppresses in favour of `pro comp erase` and `pro comp remove-mdm`. **The refusal does not name the successor**, and nothing else does either: the generator drops the specs' own `deprecated: true` on the floor, so neither `Short` nor `Long` says a word. A user whose `pro static-computer-groups list` is refused has no route to the command that works. Worth closing by surfacing `deprecated` into the refusal wording; not done here.

Those last two are worth reading as a template for the next withdrawal, because the wire disagrees with the spec and the spec is still what this CLI follows. public-apis-oas#400 removed both from `external/jpapi`, and the SDK dropped its `InitializeSystemV1`/`PlatformInitializeSystemV1` methods with it, on the grounds recorded in authorization-policies#260: each bootstraps a Jamf Pro server from an activation code, neither applies to a cloud instance, and neither appears in the capability map. The gateway still routes them — the SDK probed `{}` to each and got Jamf Pro's own `400 INVALID_FIELD` on `jssUrl`/`eulaAccepted`, with `GET /pro/v1/jamf-pro-version` as the in-run control — so `pro systems initialize` and `platform-initialize` are refused here while demonstrably answering, which is exactly the case the `unpublished` wording exists for. Neither is a command anyone should be running against a gateway-managed cloud tenant anyway.

**The `unpublished` wording is load-bearing, not decoration.** Probed 2026-08-31 (EU, tenant-scoped): `GET /pro/v1/api-roles` returns 200 with 15 roles, `/pro/v1/api-integrations` 200 with 81, `/pro/v1/api-role-privileges` 200 with the full list, and `/pro/v1/api-role-privileges/search`, `/pro/v2/mdm/commands` and `/pro/v1/macos-managed-software-updates/available-updates` all answer **Jamf's own** 400/400/503 — a Jamf-issued status being proof the gateway routed it. So a bare "not served by the gateway" reads as a CLI defect to anyone whose command demonstrably returns data; the message has to explain it is being stopped *because* it works and won't. `TestCheckAPIMatchRefusesAnUnpublishedEndpointAndExplainsWhy` asserts the explanation, not just the refusal.

**`forceServed` is the escape hatch and is empty.** Its bar is deliberately **not** "the wire says this still works" — that is the transitional state, not a counter-example. An entry asserts the published surface is *wrong*. It was the obvious reach for v1942, whose purge the SDK itself recorded as a publish-stage filter defect (`_permissions/routes.yaml` still declares all 146 with their capabilities, the OPA allow blocks are intact, 19 of 20 sampled paths answered 200 with an in-run control) — and it would have been the wrong answer, because the published surface was right and this CLI was sending a superseded version. Reaching for it would have pinned the mistake in place under a paragraph of evidence. Note too that a `forceServed` verdict carries **no `Scopes`**, so an entry silently costs those operations their 403 capability vocabulary and their `gatewayPrivileges` catalog field — the scopes come from the same withdrawn spec. Where it genuinely matters is Classic, whose spec trails the Pro one (11.28.0 vs 11.31.0): a Classic resource added since 11.28 is indistinguishable here from one withdrawn and would be refused on a stale spec. One resource is affected today (`computerconfigurations`), and the instance 404s it too, so it is dead rather than new — but a future SDK ingest lagging a Jamf Pro release is the case to watch.

**What a 403 can and cannot establish — read this before adding a `probe` entry.** An unrouted path and an under-privileged one are byte-identical: `GET /pro/v1/definitely-not-a-real-endpoint` and `GET /pro/v1/auth` answer the same 403, the same `{httpStatus, traceId, errors}` body, the same `BAD_PERMISSIONS` code and description, the same header set — only the trace id differs. A bare Tyk `404 page not found` distinguishes an unknown **namespace** (`/nosuchnamespace/v1/x`) and nothing finer. So one 403 is not a probe; an entry needs the same credential reaching the rest of the namespace in the same run, across regions.

One shape worth knowing: **Classic is judged per subtree, not per path**: five resources have no bare collection endpoint (`computerhistory`, `computerapplications`, `mobiledevicehistory`, `patchavailabletitles`, `patchreports` are reachable only as `/computerhistory/id/{}`), so the exact-path form reported five served resources as absent. Its table entries carry a `*` method and a terminal `**`, because a Classic path is assembled at runtime from the resource plus whichever lookup is in play.

The manifest also stores the **per-method gateway scopes** from `x-required-privileges` (`categories:read`, `device-actions:execute`, …), and `Coverage.Verdict` returns them. They are emitted into the runtime table as `scopeRules` and are what `gateway.Scopes(method, path)` answers — the input for the 403 vocabulary note below. Note an operation with no scope is not an absent operation: 44 Jamf Pro endpoints are unauthenticated (`/v1/health-check`, `/v1/jamf-pro-version`, `/v1/locales`) and declare none, so a lookup miss is not evidence of anything.

The whole manifest is emitted, not just the operations the generated commands send — unlike the `unserved` table beside it. The consumer is a concrete failing request, and the hand-written commands assemble paths the generator never enumerates (`pro overview` alone sends ~41), so narrowing to generated ops would leave exactly the fan-out commands with no answer. Lookup is two passes, literal patterns before parameterised ones: `/pro/v1/computers-inventory/detail` matches both `.../detail` and `.../{}`, and a single ordered scan would return whichever the sort reached first.

**A 403 has two vocabularies and neither converts to the other, so the answer follows the request rather than the command.** A Jamf Pro instance enforces API-role privileges spelled as prose (`Read Categories`), granted in Jamf Pro. The gateway enforces GA capability permissions (`categories:read`), granted in Jamf Account when the API integration is created — and the GA consolidation folded several privileges into one capability, so there is no per-row translation in either direction and Jamf Account no longer offers the old names at all. Printing the wrong one sends the operator to a console where the grant it names does not exist, which is the same class of wrong answer as `gatewayUnservedNote`'s.

Three call sites, split by what each one knows:

- `forbiddenHint` (`internal/client/client.go`) answers a Pro or Classic 403 from the capability scopes of the request it actually sent, via `gateway.Scopes`. It has to be here rather than on the command: a hand-written command fanning out over dozens of endpoints carries one annotation for the whole batch, and the annotation is the Jamf Pro vocabulary anyway. Gateway mode is read off the `/pro/` and `/proclassic/` path prefixes, the same discriminator `withGatewayUnservedNote` uses.
- `EnrichPrivilegeError` (`internal/commands/privilege_error.go`) answers a Platform command's 403 from its own `jamf:privileges` annotation, which is already the capability vocabulary. It also **maps that 403 onto exit code 5**: platform commands return the SDK's error untouched, so a permission failure used to exit 1 — the code the README documents for a generic failure, on the one failure with a specific remedy. Only 403 is remapped.
- The same function suppresses the Jamf Pro names when a hint already carries a platform answer, detected by `privileges.Marker`. Sentinel rather than threading the resolved auth method down to the error formatter, because the test wanted is "has a platform answer already been given", and that is knowable where the answer is.

The same rendering feeds the `commands -o json` catalog, which carries the requirement in both vocabularies: `privileges` (Jamf Pro API-role names, or the capability list for a Platform command), `gatewayPrivileges` (the capability slugs the gateway requires for a Pro or Classic endpoint, stamped from the manifest at generate time) and `gatewayPermissions` (those rendered as Jamf Account's picker words). The human form is not a convenience: an integration can only be created in Jamf Account's Platform API integrations UI, whose picker lists named permissions with a checkbox per action and shows a slug nowhere — so a catalog of slugs alone is not actionable. `gatewayPermissions` is rendered at runtime rather than stamped, so re-verifying the transcription against Jamf's article is an edit rather than a regenerate. Classic scopes are per **method** (`accounts:read` for a GET, `accounts:update` for a PUT) even though the served/unserved verdict is per resource, and only the methods a command *always* sends are listed — a `--name` lookup's extra read is deliberately not folded in, since the alternative is telling everyone running `delete <id>` to grant a read they do not make. `apply` is the exception: it always lists, then creates or replaces, so it carries all three.

`internal/privileges` turns a slug into the section and permission name Jamf Account's picker prints (`device-groups:read` → *Inventory > Device groups: Read*), because the picker is searched by name and the two differ substantially — `computer-inventory-collection-settings` is "Device inventory collection settings". `catalogue.go` is a hand transcription of Jamf's permissions-map article and a **rendering** table only: which capability an operation needs always comes from a spec, so a row with nothing pointing at it renders nothing, and that is why it does not conflict with the rule below against hand-supplying the account APIs' stripped privilege names. It cannot be generated — no machine-readable artefact carries the picker's names. `public-apis-oas` looks like one and is a trap: its `scopes.yaml` derives `name` by title-casing the slug (`scope.ts`'s `toFriendlyName`), so it would confidently print "Computer inventory collection settings", and it carries no section at all. terraform-provider-jamfplatform's `internal/common/permissions/catalogue.go` is the same transcription of the same article; the two are copies on purpose, since neither repo can import the other. `TestCatalogueCoversEveryScopeThisCLISends` fails when a spec starts requiring a capability with no row — it cannot check that a row is *right*, so re-verify against the article.

**Both refusals key on the resolved auth method, not on a profile, so env-var credentials behave identically.** `checkAPIMatch` type-asserts the provider (`isGatewayProvider`), which is what `JAMF_URL` + `JAMF_CLIENT_ID` + `JAMF_CLIENT_SECRET` (+ `JAMF_TENANT_ID`/`JAMF_ENVIRONMENT_ID`, or the gateway host alone for organization scope) resolve to — so a CI job using env vars gets the same refusal as a profile, and it fires before any token exchange, on invalid credentials too. What it must *not* do is name a profile: `resolveAuth`'s precedence is env-then-profile while `resolvedProfile` stays whatever `-p` or `default-profile` names, so attributing the method to it reported `profile "default" uses auth-method platform against the gateway` for a profile that is oauth2 against an instance. `credentialSource` names the real source (the `JAMF_*` variables, a `--token-file`, or the profile), and both messages put it **last** because the phrase is plural for the env-var case and singular for a profile — an earlier wording put a verb straight after it and read as broken English for exactly the CI case it was added for. `TestCredentialSourceNamesTheEnvironmentNotTheProfile` and `TestMessagesReadCorrectlyForAPluralCredentialSource` pin both.

**The reverse direction is refused too: a Platform-only command on an instance profile.** Every generated platform command already gates its `RunE` on `platform.RequirePlatformClient`, but that error explains how to *set up* a platform profile without saying the profile in hand is an instance one — so an operator with working oauth2 credentials reads it as a credential problem. `checkAPIMatch` refuses it by annotation (`jamf:api: platform-gateway` against a non-platform provider) and names the profile, its resolved auth method and `platform setup`. Deliberately not extended to the `security` namespace, whose resolver returns before this check and already hints about the base URL shape.

`internal/client`'s `gatewayUnservedNote` is the response-side half and still matters despite the pre-flight refusal: a hand-written command that fans out over many endpoints (`pro overview` makes ~41 calls, `pro backup` and `pro diff` more) carries one command annotation for the whole batch, so only the request itself knows which endpoint was refused. It is appended, never substituted, and gated on the body carrying `BAD_PERMISSIONS` or `404 page not found`.

`make verify-gateway-coverage` is the CI guard, a no-op pass when the coverage specs are absent from the drop directory (CI has no SDK checkout; the committed manifest is the contract). It checks with `git status --porcelain`, not `git diff`, because **git diff cannot see an untracked file** — the first run after adding `specs/gateway/` regenerated the manifest with different provenance and still reported clean. `TestAlmostEveryRequestResolvesAsServed` catches a manifest that is present but not matching — the failure mode has no error, it just refuses the whole Pro namespace, which is what the `serviceSegment` marker-substring bug did to generated paths. Its `gatewayOps` helper has to replay the generator's consolidation passes, not just `ParseSpec`: parsing alone counts all three `ComputersInventory{,V2,V3}.yaml` resources when only one becomes a command, and a superseded version is exactly what a spec drop withdraws — so v1942 read as 105 refusals of 811 and tripped the 10% ratio on resources that are not commands, where the shipped surface accounts for 58 of 761. Only `DeduplicateVersioned` and the two passes that rewrite a path are replayed; the rest set names, columns and lookup fields, which no verdict reads. `TestEveryOverrideStillMatchesACommandThisCLISends` fails when an override stops matching any shipped path.

**Security Cloud device-groups is at v1865, and the unrouted v2 PUT is withheld rather than the whole spec held back.** The four-build hold (v1700 through v1807) is over. What forced it is unchanged: `PUT /v1/groups/{groupId}` is deprecated in favour of `PUT /v2/groups/{groupId}` with a 2027-08-25 sunset, and **the successor is not routed** — v2 answers `403 BAD_PERMISSIONS` while v1 answers `200` with the updated group, probed 7/7 by the SDK on 2026-08-29 against a group created and deleted inside the same run, with a v1 write on the same group as the in-test control. Left in the spec, `deduplicateVersionedOps` prefers the higher version — correctly, by its own rule — and `security device-groups update` becomes that 403, with the working v1 path demoted to a `FallbackPaths` entry the platform template deliberately ignores. A 403 from an unrouted path is indistinguishable from a missing privilege, so the operator goes looking for a grant that cannot help.

So the operation is dropped at parse time instead: `platformUnroutedOps` (`generator/parser/platform.go`), keyed `{METHOD} {normalised path}`, filtered out by `dropUnroutedPlatformOps` before name disambiguation and before the dedup. `list` stays on the routed v2, everything else on v1 — the withholding is per-operation, not a version-wide hold. **This is the CLI declining to follow the SDK**, which whitelisted its `UpdateDeviceGroupV2` method so a `// Deprecated:` marker had a named successor to point staticcheck at: a library can ship a method that fails, but a CLI command that always 403s is worse than an absent one. Each drop needs a recorded probe behind it, and `TestPlatformUnroutedOpsAreDeclared` fails when an entry stops matching any shipped spec — the other way an entry goes stale, since nothing in a spec announces that routing has landed.

Two smaller things the v1865 ingest brings. `PUT /v1/groups/{groupId}` now declares the 200-with-`Group` body it always answered, so the `x-jamf-expected-status: 200` override is gone from the spec **and** `security device-groups update` finally prints the updated group instead of exiting 0 silently — the gap recorded below is closed. And `customer-id` is gone from both list ops, which empties `platformIgnoredRequiredParams`. Nothing surfaces the v1 deprecation to the user, and that is deliberate for now: a "use v2 instead" note would be advice to a 403.

**The scope travels in a header, not the URL.** Every Jamf gateway path used to embed it — `/api/{namespace}/{version}/tenant/{tenantId}/{resource}` — and Tyk resolved the request context from `path`. Prod gained `header` as an allowed source on 2026-08-25 (tyk-gateway-management `0793131b`, "JSC-73421 Enable header context support - Prod") and the published specs dropped the segment in GitOps build v1495 in favour of a required `X-Tenant-Id` header. Both forms answer during the transition window, so this repo follows the SDK onto headers only rather than keeping a selectable mode — a second code path nothing exercises is how the previous URL-shape bug survived weeks.

Three copies of that rule exist and all three moved together: `normalisePlatformPaths` (`generator/parser/platform.go`) strips `/tenant/{tenantId}` from every platform spec path — Security Cloud has already lost it upstream, blueprints/benchmarks/devices/pro/classic still declare it; `rewritePathForGateway` (`internal/client/client.go`) maps instance paths onto their gateway namespace (`/JSSResource/x` → `/proclassic/x`, `/api/v1/x` → `/pro/v1/x`) and `setScopeHeader` stamps the header on both the request and the multipart-upload path; and the SDK's `Transport.APIPrefix` replaces the old `TenantPrefix`. `TestLoadResourcesDropsTheTenantFromEveryPath` and `TestGatewayTenantTravelsInHeader` fail if a tenant segment reappears in either. Wire-verified 2026-08-25 (paths as they were then, under `/api`): Security Cloud (categories, device-groups, ztna-apps create/get/delete), Pro modern (`/pro/v1/categories` list, POST 201, DELETE 204), Classic (`/proclassic/allowedfileextensions`), Platform (`/blueprints/v1/blueprints`) and the multipart path — a real 4.6 MB `.pkg` through `packages upload`, which goes via `Client.Upload` rather than `Client.Do` and is therefore a separate header call site: `POST /pro/v1/packages/{id}/upload` answered 201 and the server-side SHA3-512 matched the local hash. **The `.pkg` upload no longer works on the GA host** — see the base URL section above.

**The audit question is settled: 27/27 covered.** The previous URL shape existed because the gateway's audit rules are path globs and version-first paths matched none of them — 19 of 27 Security Cloud mutations executed unaudited for weeks (`docs/solutions/logic-errors/securitycloud-tenant-first-url-audit-2026-08-21.md`). Header scoping is covered, and by the *other* half of each glob pair: every family declares both `/v1/<svc>/…` and `/**/v1/<svc>/…`, so a header-scoped `/v1/ztna/apps` matches the bare form (19 ops) while uem-connect's `/uem-connect/v1/…` still matches the wildcard form (8 ops). Verified by simulating the real matcher — `CompileGlob` renders `**` as `.+`, and `AuditPre` matches `stripListenPath(path)` before any rewriting — against the deployed rules in all three prod regions.

`scripts/audit-coverage.py` (`make audit-coverage`) is that simulation, kept because the answer changes whenever either side moves and is not guessable: tenant-first looks like it should match the bare globs, and does not. Run it against a **ref**, not the worktree — a local `tyk-gateway-management` checkout is easily behind the deployed state, which is the quickest route to a confident wrong answer. Validated against the pre-2026-08-21 generated code, where it reports exactly the historical 19 gaps.

**Most platform mutations are not audited upstream at all**, and that is not something this repo can fix. Only three prod api-products declare `path_glob` rules — `securitycloud`, `blueprint-management`, `ai-policy-builder` — so the 18 mutating requests the CLI sends to blueprints, devices, device-groups, device-actions and compliance-benchmarks match no rule because no rule exists. `jamf-pro` (both the `/api/pro` and `/api/proclassic` listen paths) has no audit block either, which is why moving Pro and Classic onto headers could not have cost audit coverage.

**`header` is an allowed request-context source in prod as of 2026-08-25** — tyk-gateway-management `0793131b` ("JSC-73421 Enable header context support - Prod") adds `host` and `header` alongside `token` and `path` for jamf-pro, securitycloud, blueprints-api, compliance-benchmarks, devices, device-groups and device-actions. Worth knowing when reading that repo: the commit is recent enough that a local checkout may not contain it, and the pre-commit files list `[token, path]`, which reads as "headers are not supported" and is wrong.

**Environment scope exists in the SDK and is not used here.** `internal/client.ScopeEnvironment` sends `X-Environment-Id`, and the gateway lists `[tenant, environment]` as request-context types on securitycloud and compliance-benchmarks. No SDK option sets it (`WithTenantID` is the only one) and no generated operation is environment-scoped, so the CLI cannot send it: tenant IDs stay the only exposed scope. They are expected to become legacy at Platform API GA, when one environment ID will reach several product namespaces and the per-namespace tenant split below disappears.

**Three scope levels, one per profile.** A Jamf Platform API integration is created at one of three levels in Jamf Account, and its credential only works with that level — so this is a choice between integrations, not between ways of naming the same access:

| level | header | what it reaches |
|---|---|---|
| organization | *none* — resolved from the access token | Jamf Account: `account-licenses`, `deal-registrations`, `distributor-*`, `sso-connections`, `sso-domains` (US-only), plus AI Governance |
| platform environment | `X-Environment-Id` | a group of tenants across product types — **the level to prefer**; also the only level `platform audit` accepts |
| tenant | `X-Tenant-Id` | one Jamf Pro / School / Protect / Security Cloud tenant — the legacy level |

`platform setup` asks for the environment ID first and **stops there if it gets one** — the levels are mutually exclusive, so asking for a tenant next would offer a combination no credential can use (`promptScope`). `auth.Scope` (`internal/auth/scope.go`) carries the pair and answers `Header()`, which returns `("", "")` for organization scope — an empty header name is a correct answer there, not a missing value. `resolveScope` reads `JAMF_ENVIRONMENT_ID` / `JAMF_TENANT_ID` then the profile's `environment-id` / `tenant-id`. **Organization scope has no ID to read, so the gateway host is what selects platform auth for it** — `isPlatformGatewayURL` (`internal/commands/platform.go`). Before that, `ResolveAuthForProfile` entered platform mode only on a profile's `auth-method: platform` or on a tenant/environment ID, so an organization-scoped credential supplied purely through `JAMF_URL` + `JAMF_CLIENT_ID` + `JAMF_CLIENT_SECRET` fell through to oauth2 against a URL that is not a Jamf Pro instance. Nothing exercised it until the Jamf Account commands arrived — they are the first organization-scoped-only surface, and CI/CD is exactly the env-var case. An explicitly supplied level (flag or env var) **replaces** the profile's rather than joining it: `JAMF_ENVIRONMENT_ID` against a tenant profile has to mean "use this environment", the way every other env var here overrides the profile, and merging the two instead reported a mutual-exclusion error for a perfectly sensible override (`scopeFromParams` in `ResolveAuthForProfile`). What is refused is two levels supplied *together*; `checkScopeConflict` refuses both-at-once, in the environment as well as in a profile, because precedence would hide the mistake and the symptom is a 403 from whichever half the credential does not match. Both clients honour it: the platform SDK gets `WithEnvironmentID`/`WithTenantID`/neither, and the CLI's own Pro/Classic client takes `client.WithGatewayScope` — gateway mode is a separate flag from the scope, since an organization-scoped credential is gateway auth with no header at all.

A customer with several tenants and no platform environment therefore keeps a profile per tenant, as before.

**A hand-written command can still hold a stale path, and the old shape hides it.** `pdgListPath` (`internal/commands/pro_platform_device_groups.go`) was building `/device-groups/v1/tenant/{id}/device-groups` from the SDK's `Transport().TenantID()` for months after the scope moved into a header, and nothing failed: the path form is still routed during the transition window. It only breaks for the scope Jamf wants integrations to use — `TenantID()` answers `""` for environment scope *and* for organization scope, so the path collapsed to `/tenant//device-groups`, which the gateway answers **301** rather than anything a caller can act on. Prefer the SDK's `Client.Scope() (ScopeKind, string)` (v0.18.0) over `TenantID()` for exactly this reason: an accessor for one kind cannot express a three-valued property. `TestLoadResourcesDropsTheTenantFromEveryPath` covers the generated commands only; hand-written path builders need reading. Tenant scope is not deprecated — some surfaces are only reachable that way — but new integrations should not choose it by default.

Wire-verified 2026-08-26 on the sandbox's tenant-scoped credential: tenant scope sends `X-Tenant-Id` and works; the same ID under `JAMF_ENVIRONMENT_ID` sends `X-Environment-Id` instead and the gateway answers 404 for `GET /securitycloud/v2/groups`; an organization-scoped profile sends **no** scope header and earns `400 REQUEST_CONTEXT_NOT_PROVIDED`, which is what proves the header is genuinely absent. **Environment scope is now verified end to end**, on 2026-08-31 against an EU sandbox environment-scoped credential (`JAMF_ENVIRONMENT_ID` + client credentials, no profile): `pro blueprints list`, `pro categories list` through the gateway, and the whole AI Governance surface all answered 200. The same UUID sent as `X-Tenant-Id` answers `403 OWNERSHIP_FORBIDDEN` and sending both headers answers the same 403, so the levels really are exclusive on the wire and not merely by policy; with no scope header the answer is `400 REQUEST_CONTEXT_NOT_PROVIDED`. A gateway token is opaque (342 bytes, not a JWT) and carries an empty `scope`, so nothing about which level it belongs to can be read off the token — the header is the only signal, and a mismatch is only discoverable by sending it.

**Which setup command owns what.** `platform setup` owns everything gateway — region, client credentials and the one tenant — and is the entry point for the gateway-served commands. `security setup` owns the Radar application pairs only, and closes by pointing at `platform setup`. After validating credentials, `platform setup` does one read against `content-categories` and **reports** whether this tenant reaches Security Cloud rather than passing or failing on it: a Jamf Pro tenant legitimately cannot, and the gateway's two rejections (`OWNERSHIP_FORBIDDEN`, `BAD_PERMISSIONS`) are indistinguishable in intent from there. The answer drives the closing summary, so the profile describes what it actually enables instead of what was typed into it. It runs with retries disabled, so a mistyped secret fails immediately rather than after the SDK's retry sequence — worth doing even now that the sequence is bounded at ~22s (see the retry note under Jamf Account and Audit), because at an interactive prompt that is 22s spent on an answer that will not change.

`resolveSecurityClient` builds the platform SDK client independently of the scoped pairs, so a profile may carry either set or both; the product only refuses to start when neither is configured.

**A new endpoint version takes the plain command name; the old one is dropped.** This is the Jamf Pro rule (`deduplicateVersionedOps`), and it applies to the gateway unchanged: the highest version of an endpoint wins, the lower version stops being a command, and its path is recorded on the winner as a `FallbackPaths` entry. So Security Cloud's device groups expose one `list`, served by `GET /v2/.../groups`, not a `list` on the deprecated v1 beside a `list-v2` on its successor — the unversioned name has to point at the endpoint that is not dying, or the v1 sunset breaks the *primary* command name and forces everyone onto a differently-named one.

Two things made that dedup silently not fire here, both now fixed in `generator/parser/parser.go`. `stripVersionPrefix` only strips a *leading* version, which fits Jamf Pro (`/v1/computers-inventory`) but not the gateway, where the version follows the service namespace (`/securitycloud/v1/groups`) or the tenant (`/securitycloud/uem-connect/v1/connectors`) — so the two versions hashed to different keys. And `compareAPIVersions` ranked by the leading segment, scoring every gateway path 0, which made "prefer the higher version" a tie decided by map iteration order. Both now read the version wherever it sits (`stripVersionSegments`, `apiVersionRank`); across all Jamf Pro specs and every platform spec this introduces exactly one new collision, the one it is meant to catch.

`FallbackPaths` is populated for platform GETs and deliberately ignored by `generator/platform/template.go`. Pro retries a displaced older path on 404 because customers run older Jamf Pro versions; the gateway is a single deployment with no such version skew, so there is no tenant that has v1 but not v2. An unrouted path answers 403 `BAD_PERMISSIONS`, which is indistinguishable from a real privilege failure — falling back on that would turn a permission problem into a silent downgrade, the same class of failure as the `baselineId` rename answering 0 rules with no error. The corollary is `platformUnroutedOps`: when the *preferred* version is the unrouted one, the answer is to withhold that operation before the dedup sees it, not to let it win and fall back.

**Known upstream gaps** (wire-probed 2026-08-20, tenant `wisconsam`, unless noted):

- Pagination is under-declared. Ten list ops return a paged envelope (`totalCount` + `results`) but only `sync/runs` declares `page`/`page-size`. On the wire only `ztna/apps` honours them; `categories`, `ztna/predefined-apps` and `ztna/shared-gateways` demonstrably ignore both and return everything. `ConnectorPage` and `SyncRunPage` are structurally identical yet only the latter declares the params — the tell that this is an omission. Re-probed 2026-08-20: unchanged, and `GET /v2/.../groups` joins the list — it returns a `{groups: []}` envelope with no `totalCount` and ignores both params.
- `risk override` declares `deviceIds` as an array with **no `items` schema at all**, so `--scaffold` can only render `[]` and nothing can say what an element looks like. The one array in the Security Cloud surface that is opaque for an upstream reason rather than by design — every other remaining `[]` is an array of plain scalars (IDs, IPs, hostnames, subnets), which `parser.ScaffoldJSON` leaves empty deliberately.
- `--set` cannot express a top-level-array request body (the two DNS whole-list replaces), because it builds an object. `--file` is the only route; `--set` on those endpoints fails with `400 [INVALID_FIELD] Request body could not be read`.
- `uem-connectors create` cannot be built from the published spec at all, and the failure is a **500 rather than a validation error**. `authStrategy` and the credentials under `deviceSyncAuth` are absent upstream; the SDK restores both (`schemaCreations`/`schemaPatches`, self-expiring via `schemaPatchesRequireAbsent`), which is why `--scaffold` renders them as of the v1439 ingest. The error ladder, re-probed here 2026-08-24: no `authStrategy` → `500 INTERNAL_ERROR`; `authStrategy` with no `deviceSyncAuth` → `422 VALIDATION_FAILED ": invalid auth configuration for Jamf PRO"`; a complete body → `409 CONNECTOR_CONFIG_ALREADY_EXISTS`, because **a tenant holds at most one connector whatever its vendor** and that pre-check runs after auth-config validation but before the credentials are checked against the UEM instance. The 500 used to be unreportable as well as slow — the CLI nested its own retryablehttp client inside the SDK's, which retried the POST four times and then swallowed the response, so the answer took past a 2-minute timeout and arrived with no `traceId`. Fixed; it now answers after one attempt with the traceId in the message. The secret belongs in `--file`: `--set deviceSyncAuth.clientSecret=…` puts it in shell history and `ps`, which is what the credential policy at the top of this file exists to prevent — and `authStrategy: M2M` avoids the question entirely, taking a `tenantId` and no credentials (see the resolved note below) — **at the cost of leaking a Jamf Pro API integration per create.** M2M self-provisions an API role and integration on the named Jamf Pro, and **that integration survives the connector's DELETE**: the SDK's test tenant had accumulated 97 enabled "JSC Connector" integrations against zero live connectors, 88% of every integration on the instance (2026-09-01). Nothing in this CLI creates or cleans those up, and nothing in the connector response points at one, so `pro api-integrations list` against the target instance is the only way to see them — a command the gateway does not publish, so it needs an instance profile. Reported upstream as a security finding. Worth saying out loud before recommending M2M for repeated create/delete cycles. A read returns `clientId` and `username` but never a secret, so a `JAMF_PRO_OAUTH` connector still cannot be exported and re-created; an `M2M` one can, since `tenantId` is on both the request and the response.
- The ZTNA app's `security` block declares `additionalProperties: false` as of v1439 and the **server does not enforce it**: a create carrying `security.bogusKey` answers 201 and silently drops it (probed 2026-08-24, the app read back with the three declared sections and nothing else). So a mistyped `--set security.riskControls.enabld=true` is accepted and does nothing, with no wire feedback at all.
- `ztna-apps create` requires `categoryName`, and the spec gives it no `example`, so `--scaffold` renders `"categoryName": ""` — the one value the server explicitly rejects (`400 [INVALID_FIELD] categoryName: must not be blank`). Every scaffold is a template to edit, but this is the field where the rendered value is *guaranteed* invalid rather than merely incomplete; `Uncategorized` is what the tenant's own apps carry.
- `ipsec.left.subnets` is still capped at one element while `right` is not, and the rejection names neither the field nor the cardinality: two left subnets answer `400 [INVALID_FIELD] field=ipsec "IPSec configuration is not valid."` (probed 2026-08-24). Deep IPSec validation **does** run alongside a missing required top-level field — a create omitting `contact` and carrying a public left subnet reported both errors in one response — so a probe written to expect only the top-level failure will see more than it asked for.
- **`ztna-apps` `name` and `predefinedAppId` together is accepted, not rejected.** v1582 declares `name` "must be null or omitted when `predefinedAppId` is set", with a 400 for the combination. On the wire it is a **201 that silently drops the name** — probed 2026-08-25 with an unused template: the app read back `name: null` with the template applied. Same silent-drop class as the `security` block's unenforced `additionalProperties: false`, and the same consequence: a caller who names a predefined-derived app gets no feedback that the name went nowhere. Reusing a template another app already holds *is* refused, `409 [CONFLICT] Resource already exists.`, and that check runs before body validation.
- **`--name` can never reach a predefined-derived ZTNA app, and the error does not say so.** v1582 declares `App.name` required *and* nullable, which is the spec catching up with the wire: an app created from a `predefinedAppId` inherits its name from the template and returns `name: null` (both apps on the sandbox are of this kind). `platform.ResolveIDByName` filters the collection by name, so those apps are unreachable by `--name` and the failure reads `not found: no item with name "…"` — indistinguishable from a typo. Use the ID. Worth fixing in the resolver one day by counting nameless items and saying so.
- Neither `dns-zones create`'s 422s (`GATEWAY_NOT_FOUND`, `NAMESERVER_IP_RESTRICTED`) nor its validation rules are documented in the spec. A zone's `nameServers[].ip` must be **publicly routable** — `10.0.0.53` is rejected `NAMESERVER_IP_RESTRICTED`, `198.51.100.53` is accepted. Note this is the inverse of the ZTNA IPSec rule, where `ipsec.left.subnets[]` must be private.

**Resolved since the 2026-08-18 probe:**

- **`security device-groups update` prints the updated group again, and `customer-id` is gone.** The v1865 spec declares `PUT /v1/groups/{groupId}`'s 200-with-`Group` body itself, so `successStatus` finds a schema for the status it expects and the command renders what the server returned — it used to exit 0 printing nothing while a following `get` showed the new name, because the spec described a body only under 204 and the `x-jamf-expected-status: 200` override supplied the status without one. Third time in five builds that a silent SDK override became redundant, which is the argument for diffing the override tables at every ingest and not only the schemas. The same spec drops `customer-id` from both list ops — declared required while the scope decided the customer — so `platformIgnoredRequiredParams` is now empty; the knob stays for the next one.
- **`uem-connectors create` is a discriminated union as of v1882, and the CLI now scaffolds the Jamf Pro branch.** Upstream adopted what the SDK had been patching in: the request body is `ConnectorCreateRequestBody`, a bare `oneOf` over `JamfProConnectorCreateRequest` (fully typed, `additionalProperties: false`) and the generic `ConnectorCreateRequest`, discriminated on `vendor` — which is also why `JAMF_PRO` is gone from the generic branch's vendor enum. A bare `oneOf` carries no properties of its own, so **the whole body parsed to nothing and the command silently lost `--scaffold` and every "Allowed values:" line**, with `make generate` exiting 0. `parseSchemaDepth` now adopts the *first* variant as the schema's own shape — a scaffold has to be a body that pipes into `--file`, and merging branches renders one that satisfies neither — unions the branches' enum values (the discriminator is the field where naming one variant's value would read as "the other nine vendors are invalid"), and records `Variants`/`Discriminator` so the help says which shape `--scaffold` shows. A field only a sibling variant declares is carried enum-only as `VariantOnly` and kept out of the scaffold. Two things to re-probe rather than trust: upstream now marks `tenantId` **`writeOnly`**, which contradicts the 2026-08-28 probe recorded below that `tenantId` on the *response* is what distinguishes an `M2M` connector from an OAuth one; and `BASIC` is now documented as a usable Jamf Pro strategy (`username`/`password`), where this file previously recorded two.

  **v1981 finished the split, and it is breaking upstream while inert here.** The generic `ConnectorCreateRequest` and its vendor enum are deleted and all ten vendors now have their own request schema, so the `oneOf` is a 1:1 discriminator mapping — `--help` goes from "one of 2 shapes" to "one of 10", naming each. The v1882 handling holds unchanged, which is the point of recording it: the first variant is still `JamfProConnectorCreateRequest` and still the only one wire-verified, so `--scaffold` renders the branch a caller can actually use. It is also **self-consistent now** where it was not: the scaffold used to pair a spec-example `authStrategy: M2M` with a `deviceSyncAuth` block only `JAMF_PRO_OAUTH` uses, a template with one of two halves to delete. It now renders `JAMF_PRO_OAUTH` alongside that block, with `tenantId`, `url` and `isoCountry`. One deletion is still needed: `deviceSyncAuth` carries `clientId`/`clientSecret` *and* `username`/`password` together, being the union of the OAuth and BASIC credential pairs. The unioned `authStrategy` enum also picked up three values from the new Citrix/XenMobile variants — `USERNAME_PASSWORD`, `CITRIX_CLOUD_ADMIN`, `CITRIX_CLOUD_ADMIN_OAUTH` — which are **not** Jamf Pro strategies, so the "Allowed values:" line for a union field spans every variant and is wider than the shape `--scaffold` shows. That is the honest rendering of a discriminated union in flat help text, not a bug, but it is a trap when reading it.

- **The v1958 sync-interval enums reached the CLI with the v1981 ingest.** `uem-sync-settings update` now lists `refreshRateMinutes: 60, 120, 240, 480, 720, 1440` and `deviceUnmanagedThreshold: 0, 1, 3, 5, 7, 14` in `--help`, where `refreshRateMinutes` was previously `minimum: 1` and unconstrained in the help text. Field types are unchanged, so this is not breaking. **`deviceUnmanagedThreshold` was redefined under the same name**, though: it meant "consecutive syncs absent, 0 disables the grace period" and now means "days since last check-in, 0 uses the platform default (3 days)" — the unit changed and `0` flipped from off to default-on, so a caller who sent `0` to disable the behaviour now gets three days. The spec also claims the field does not apply to `JAMF_PRO`.

  **Both halves are wire-verified as of 2026-09-01, on a connector created for the purpose, and the two fields behave completely differently.** `refreshRateMinutes` enforces its enum: 60 and 1440 answer 204, while 360, 59, 1, 100000 and 0 answer `422 VALIDATION_FAILED` — and the description leaks the accepted set while `field` stays null, so the error names the constraint without naming what violated it. `deviceUnmanagedThreshold` is **silently ignored for `JAMF_PRO`**: 3, 7, 14, 1 and 0 each answer 204 and each read back as 0. So the spec's "not applicable to JAMF_PRO" is real and it is enforced by discarding the value, not by refusing it — a caller setting a grace period on a Jamf Pro connector gets a success and no grace period, with the enum in `--help` implying otherwise. That also **refutes the 2026-08-28 probe recorded here as having stored the value**; the service changed underneath it, which is the case for re-probing a "resolved" note rather than trusting it. Reaching these at all needed a real connector: the doomed-request technique does not work on this operation, since five PUTs to a bogus `configId` with in-enum, out-of-enum and below-minimum values all answered the same `404 NOT_FOUND` — resource resolution runs *before* field validation here, the reverse of the ordering that technique relies on.
- **`uem-connectors create` has a credential-free path, and `uem-sync-settings update` stopped silently resetting a field.** Two SDK wire patches on top of v1700, both restored from probes on 2026-08-28. `authStrategy` gains its enum (`M2M`, `JAMF_PRO_OAUTH`, `BASIC`, dumped by the server's own 422 for an unknown value) and it now renders in `--help`, plus `tenantId` on the create request: with `authStrategy: M2M` the caller names the target Jamf Pro by platform tenant and supplies **no credentials at all** — Security Cloud provisions its own API role and integration — and `url` is then ignored, including as `""`. Note `authStrategy` is a provisioning instruction, not round-tripping state: a connector created with `M2M` reads back as `JAMF_PRO_OAUTH`, and `tenantId` on the response is the only thing that distinguishes the two forms. **The scaffold now renders both strategies at once** — `authStrategy: M2M` from the spec example, beside a `deviceSyncAuth` block only `JAMF_PRO_OAUTH` uses — so it is a template where one of the two halves has to be deleted, not merely filled in. And `concurrentSyncEnabled` joins the update request: it was on the response, absent from the request, and writable, so because the update is a full replacement a body built from the unpatched spec reset it to its default on **every** write, discarding the operator's choice with no error to notice.

Confirmed 2026-08-24 on apps and gateways alike.

#### Jamf AI Governance

Twelve generated commands from `ai_governance_policies_api.json` (SDK build v1877), wired under **`platform`, not `pro`** — `platform ai-policies` (`aip`) and `platform ai-tools` (`ait`). That is the one place this surface departs from "Platform API commands live under `pro`", and deliberately: AI Governance is not a Jamf Pro surface. It is scoped at the organization or platform-environment level, its privileges are its own (`ai-policies:{read,create,update,delete}`), and the credential this was verified with names no Jamf Pro tenant at all — `pro ai-policies` would have implied a Jamf Pro instance that need not exist. Aliases live in a new `platformAliases` map (`aliases.go`), groups under `groupPlatformAI` in `platformGroups`.

Two ingest knobs it needed, both because the paths are shaped unlike anything else in the tree:

- **`platformResourceNameOverrides` keys are the full service** — `ai/governance/policies/policies` → `ai-policies`, `.../tools` → `ai-tools`. The tags are bare nouns, and `policies` collides with Jamf Pro's own.
- **`platformOperationNameOverrides` for four ops.** A collection sub-path and its `{id}` child are both GETs carrying a path param, so both infer `get`, and neither disambiguation pass can separate them: they key on a shared non-param terminal segment and the child's terminal is `{versionNumber}`. Without the overrides the load fails outright — `platform resource "ai-policies" has two "versions" operations` — which is the right failure, but the names it wants are a judgement call, so they are written down: `versions`/`version`, `deployment`, `schema`.

**`version` as a subcommand name was a silent auth bypass, now fixed.** `chainSkip` in `root.go` matched command names *anywhere* in the chain, so `platform ai-policies version` skipped auth resolution entirely and then failed at its own gate with "this command requires platform gateway auth" — sending the operator to fix credentials that were already correct. `version` and `commands` are now in a `rootOnlySkip` set, matched only as a direct child of the root; `config`, `setup` and the rest still match anywhere, which is what they are for. Nothing about the spec or the generated code was wrong, which is why `TestChainSkip_RootOnlyNamesDoNotSkipNestedCommands` asserts the *auth-resolution* error rather than absence of an error, with the reverse case pinned too. Any future generated operation whose name is an ordinary English word already used at the root hits this — the fix is to add it to `rootOnlySkip`, not to rename the operation.

**The `commands` catalog had the same bug in its own walker, found while counting gateway refusals.** `collectCommands` skipped every command named `commands` at any depth rather than only the root's own catalog command, so `pro mdm-commands commands` — a real generated operation, and one the gateway refuses — was absent from `commands -o json` entirely: the machine-readable listing was missing exactly the entry a reader consults it for. Now conditioned on being a direct child of the root. `help` stays unconditional, because cobra gives every command one. `TestCommandsCatalogIncludesANestedCommandNamedCommands` pins both halves.

**`platformTableColumns` was keyed on the wrong thing and said nothing about it.** The key is documented as the namespace plus the resource name, but it was built from `serviceFromPath`, which returns only the *first* path segment. A three-segment namespace therefore produced `ai/ai-policies`, matched no entry, and emitted a list with no columns — indistinguishable from having written no entry at all. `namespaceFromPath` now returns the whole namespace (everything before the version segment), which also makes `ddm/report/…` and `securitycloud/uem-connect/…` keyable; `serviceFromPath` stays as-is because `apiLabel` genuinely wants the first segment ("securitycloud" is the product whichever sub-namespace an op sits in). `TestPlatformTableColumnKeys` fails on any key that matches no live list op, which is the guard that was missing.

**Wire facts**, probed 2026-08-31 on the EU sandbox with an environment-scoped credential. All twelve operations answered; the whole surface is exercised through the CLI, writes included.

- **`patch` replaces `settings` wholesale — it does not merge.** The method is PATCH and the CLI sends `application/merge-patch+json`, but the server treats `settings` as a full replacement: seed `{permissions:…, env:…}`, patch with `{permissions:…}` alone, and `env` is gone. `name` and `description` *are* leave-unchanged-if-omitted, so the two halves of one request body behave differently. Both `schemaVersion` and `settings` are required (`400 VALIDATION_FAILED … must not be null` / `must not be blank`), so there is no partial-edit request to build in the first place — **`--set settings.x=y` silently discards every other setting**. Read with `get`, edit the whole `settings` object, send it with `--file`.
- **A draft is separate from a published version.** `create` and `patch` write a draft (`hasDraft: true`, `currentVersionNumber: null` on a fresh policy); `publish` turns the draft into an immutable version and takes **no request body**. Publishing with nothing pending answers `409 NO_DRAFT_TO_PUBLISH`, so `publish` is not idempotent.
- **Whether an unknown `settings` key is rejected is the vendor schema's decision, not the API's.** `com.anthropic.claudecode` declares `additionalProperties: true` and stores a bogus key silently; `com.anthropic.claudefordesktop` omits the keyword (same effect); `com.openai.codex` sets `false` and answers `422 SCHEMA_VALIDATION_FAILED "property 'foo' is not defined in the schema"`. So a typo in `--set settings.…` is caught for some tools and silently persisted for others — read `platform ai-tools schema <toolId> <schemaVersion>` to know which. A *declared* field with a bad value is always caught, and the error names the enum: `422` on `/permissions/defaultMode` lists all eight legal modes.
- **Pagination and sort are honoured** — genuinely unusual on this gateway, where most list ops ignore both. `page` is 0-based, `totalCount` is the unfiltered total, and `sort` is `property:(asc|desc)` over `createdAt`/`updatedAt`/`name`, with anything else a `400 VALIDATION_FAILED`. The generated `list` auto-paginates at 100.
- **`schema-drift` is a flag, not a boolean filter.** `schema-drift=true` narrows to drifted policies; `false` — and `maybe`, which is not rejected — returns everything. The generated `--schema-drift` only sends the parameter when true, which is correct by accident rather than design: keep it that way.
- **`delete` is an archive and is not idempotent.** 204, then the policy is invisible to `get` and `list` alike, and a second `delete` answers `404 POLICY_NOT_FOUND`.
- **`href` on `create` and `publish` is populated by the service, not by the gateway's href-injection plugin**, so the gzip bug that nulls `href` on Security Cloud creates does not apply here. Neither call returns a `Location` header.
- **The error envelope is the service's own: `{traceId, errors}` with no `httpStatus`**, unlike the gateway's `{httpStatus, traceId, errors}`. Codes are specific and worth knowing: `TOOL_ID_UNKNOWN`, `SCHEMA_VERSION_UNKNOWN`, `SCHEMA_VALIDATION_FAILED`, `POLICY_NOT_FOUND`, `NO_DRAFT_TO_PUBLISH`.
- **One undeclared status.** `GET /tools/{toolId}/schemas/{schemaVersion}` for an unknown version answers **422 `SCHEMA_VERSION_UNKNOWN`**, where the spec declares only 404 for that operation. `GET /tools/{toolId}` for an unknown tool does answer 404. A non-UUID `policyId` is a 404, not a 400.
- **`ai-tools schema` returns ~250 KB of JSON Schema** for `com.anthropic.claudecode`. There is no table shape for it and none is offered; it is a raw JSON read.
- **`ai/governance/visibility` is routed** (403 `BAD_PERMISSIONS` on this credential, which holds the policies grants) and still has no published spec — the tell that `ai/governance` is the product and `policies`/`visibility` are capabilities beneath it. The hyphenated `ai-governance/policies` remains a bare `404 page not found`, which is what v1877 fixed in the spec's `servers` block.

#### Jamf Account and Audit

Twenty-two generated commands from four SDK specs, ingested 2026-08-31 and wired under **`platform`** alongside AI Governance: `account-licenses` (`lic`), `deal-registrations` (`deals`), `distributor-configuration` (`dcfg`), `distributor-purchase-orders` (`dpo`), `distributor-quotes` (`dq`), `sso-connections` (`ssoc`), `sso-domains` (`ssod`) and `audit`. Under `platform` for a stronger reason than AI Governance had: the account trio is **organization-scoped**, so the credential reaching it sends *no scope header at all* and names no Jamf Pro, School, Protect or Security Cloud tenant. Groups are `groupPlatformAccount` ("Jamf Account (US-only):") and `groupPlatformAudit`.

**`platform audit` is not `pro audit`.** `pro audit` runs cross-resource health checks on a Jamf Pro instance (`internal/commands/pro_audit.go`); `platform audit` reads the platform's audit *event log*. Different namespaces, so no technical conflict — but `newAuditCmd` was already taken, which is why the platform one is `newPlatformAuditCmd`.

Every spec's tags are bare nouns, so the ingest needed both override tables. `platformResourceNameOverrides`: `licensing/licenses` → `account-licenses`, `sso/connections` → `sso-connections`, `sso/domains` → `sso-domains` ("connections" is already a Jamf Protect concept, "licenses" reads as a Jamf Pro one). The partners spec needs no entry — its four tags name themselves. `platformOperationNameOverrides` for five ops: audit's `list`/`transaction`, SSO's `allocation`, and the distributor configuration's `get` plus `validate`.

**Applying an override before the derivation passes let a pass silently undo it.** Audit exposed it: `/audit/v1/audit` and `/audit/v1/audit/sources` are both no-param GETs, so both derived `list`, and `resolveNoParamConflicts` renamed *both* to their terminal segment — discarding the override that named the first one `list` and shipping the stutter `platform audit audit`. Nothing failed; the command was merely misnamed. Overrides are now applied *last*, in `applyPlatformOperationNameOverrides`, after `disambiguateSameTerminalOps` — an override is by definition the final word on a name. A collision an override introduces is still caught, by the platform generator's duplicate-operation check downstream. `TestPlatformOperationNameOverridesWinOverDerivation` asserts the resulting *name* rather than the absence of an error, since absence of an error was exactly the old symptom. Re-ordering changed no existing command: AI Governance's and UEM Connect's overrides are path-keyed and idempotent.

**`--name` is emitted on a structural test, and the test is not sufficient.** The platform emitter adds the flag whenever an operation takes exactly one path param and its resource has a list op — which says nothing about whether that param is a name-resolvable ID. Both new specs broke it, in opposite directions, and both broke *silently*:

- **The collection has no name to match.** Audit events carry no name-ish property under any spelling, and its list additionally requires a `since` parameter the lookup does not send, so `--name` on `audit lineage` or `audit transaction` was a flag that could only fail — against positionals (`resourceId`, `txId`) that are not names.
- **The positional already *is* the name.** `sso-domains allocation` takes a `{domain}` hostname, so resolving a name to the domain's integer ID and substituting it produced `GET /sso/v1/domains/allocation/1552` and a `404 "Domain not found"` — the flag actively broke a call that works when the domain is passed positionally.

Both are dropped by `platformNoNameLookup` (`generator/platform/emitter.go`), keyed `{METHOD} {path}` — op-level, not resource-level, because `sso-domains`' *other* two `--name` flags are wanted. Those needed the second knob: `platformNameLookupFields` names the property to match, because a domain's identifier is its `domain` property and `ResolveIDByName` only tries `name`, `title` and `displayName`. Named per resource rather than added to that default list, since a global `domain` match would let any resource carrying an unrelated domain property resolve on it.

**And the ID was not a string.** With the name finally matching, `--name` still reported `no item with name "example.com"`: an SSO domain's `id` is a small **integer**, every other platform resource keys on a UUID, and `extractID`'s type assertion to `string` failed — so `firstMatch` counted zero matches and the error read as a typo rather than as an ID it could not parse. `idString` now handles `string`, `json.Number` and `float64` (formatted without an exponent). This was latent for every platform resource, not only this one.

Two other ingest notes. `distributor-configuration` is a singleton `detectSingleton` does not recognise — it requires a GET paired with a **PUT**, and this is GET + PATCH — so its collection-shaped GET came out as `list` and is renamed by override; leaving `IsList` true is harmless, because the platform emitter only consumes it for `ListArrayKey` and the response is a plain object. And audit's `X-Environment-Id` is a `$ref`'d **header** parameter, which the platform emitter ignores (it emits query params only), so it correctly produces no flag.

**The account trio is US-only, permanently, and `requireUSGateway` refuses a non-US profile before sending.** Licensing, partners and SSO are organization-level APIs served from one region; the `account` tyk product ships only `use1` api-definitions and always will. This is not a rollout gap — do not re-probe EU or APAC expecting it to change. Wire-checked 2026-08-31 with an organization-scoped US credential: every account path answered on `us.api.jamfcloud.com`, and EU and APAC answer a bare `404 page not found` for all three. That is Tyk's unrouted response, with no `traceId` and no `{httpStatus, traceId, errors}` envelope, so it reads as a wrong path rather than as a wrong region — which is why the guard exists rather than a help note alone. `applyAccountUSOnly` (`internal/commands/platform_account.go`) appends the constraint to every leaf's `Long` and wraps every leaf's `RunE`; the group title carries it too, so `platform --help` says it without opening a subcommand. The guard passes through a **nil** platform client rather than inventing a region complaint, because `--scaffold` runs without auth and every other unauthenticated path has a clearer error already waiting in `platform.RequirePlatformClient`.

**Organization scope was unusable from env vars, and nothing had exercised it.** `ResolveAuthForProfile` entered platform mode only via a profile's `auth-method: platform` or a tenant/environment ID — and an organization-scoped credential names no ID by definition, so `JAMF_URL` + `JAMF_CLIENT_ID` + `JAMF_CLIENT_SECRET` fell through to **oauth2 against a URL that is not a Jamf Pro instance**. The account commands are the first surface that is organization-scoped only, and CI/CD is exactly the env-var case. `isPlatformGatewayURL` (`internal/commands/platform.go`) now makes the gateway host itself a request for platform auth. It matches the `.api.jamfcloud.com` **suffix** rather than `platformGatewayRegions`, so a region Jamf adds later needs no code change; it cannot collide with an instance URL, since an instance is `<tenant>.jamfcloud.com` and reaching a two-label `.api.jamfcloud.com` would take a tenant literally named `api` *with* a subdomain beneath it.

**Audit's blocker is gone — the header works now.** CLAUDE.md previously recorded audit as routed but unreachable with header scoping, on the grounds that its allowed request-context sources were `[token, path]`. That is no longer the behaviour. Probed 2026-08-31 in US: `X-Environment-Id` is accepted and all four ops answer `403 BAD_PERMISSIONS` (routed, credential merely lacks `audit:read`), while `X-Tenant-Id` is refused with **`400 INVALID_REQUEST_CONTEXT_TYPE` "Request context type 'tenant' is invalid. Expected any of 'environment'"** — which is the proof the header is read, since an ignored header could not produce a complaint naming its value. Unlike the account trio, audit is routed in **every** region (EU and APAC answer `401` for a US token, not `404`).

So audit is reachable only from an **environment**-scoped profile, and the spec disagrees: `audit_api.json` declares `x-scope-types: [environment, organization]`, as does the gateway's own api-product, yet organization is not accepted from a header. An organization-scoped profile therefore earns `400 REQUEST_CONTEXT_NOT_PROVIDED` — a message that says a scope was not found without saying which kind would work, while the spec a reader checks lists theirs as allowed. `annotateAuditScopeError` (`internal/commands/platform_audit.go`) names the one level that works. It deliberately does **not** annotate `INVALID_REQUEST_CONTEXT_TYPE`: that error already names both the level sent and the level expected, so there is nothing to add.

**The distributor operations answer an undocumented 400 that names an internal scope, and it is an upstream prod bug rather than an entitlement signal.** Five of the seven `partners` ops are distributor-only, and every one of them — including PATCH, and including calls carrying a bogus id — answers `400 {"error":"invalid_scope","error_description":"Invalid scopes: skyway-use2-product"}`. Three pieces of evidence say what that is:

- `public-apis-oas` documents the non-distributor answer as **`404 DistributorNotFound`** ("requests will be forbidden" when the org is not a registered distributor), plus a `500 UpstreamError`. The 400 is documented nowhere.
- Prod's Skyway scope is `skyway-use1-product` / `skyway-product` (`prod/api-products/skyway/api-definitions-use1.yaml`). **`skyway-use2-product` exists only under `dev/`.** No account api-definition references Skyway at all, and partners' `target_url` is `https://account.jamf.com/api-external/v1/partners`.
- `/auth/token` refuses **every** Skyway scope with the same message shape — `Invalid scopes: <verbatim what was requested>` — so the string in the 400 is what jamf-account asked *its own* issuer for and was refused, not a scope the caller is missing. Probed 2026-08-31: `skyway-use1-product`, `skyway-product` and `account-api-external-product-us` are all refused identically, and prod's Skyway definitions are tagged `internal-use1` against a different JWT source, so no external customer *or distributor* credential can hold one.

Conclusion: prod jamf-account's distributor controller requests a dev-deployment Skyway scope and fails, and nothing on the caller's side changes the answer. The ops still ship — they are documented, carry their own `distributor-actions:{read,create,update}` privileges, and there is a real credential class for which they are meant to work — but `annotateDistributorScopeError` appends an explanation, because the untreated form sends an operator hunting for a scope that does not exist in prod. It is gated on **both** `invalid_scope` and `skyway` rather than on the status: a 400 from these endpoints can legitimately mean a malformed purchase order, so a false positive costs a paragraph instead of a confidently wrong exclusive answer. Fixes are expected upstream — re-probe and re-verify rather than trusting this paragraph after the next ingest.

**`sso-connections` is a hard 502 on this org**, 8/8 including with a bogus id: `{"classification":"NONE","fields":[],"message":"An upstream service returned an error"}`. All five ops. `GET /sso/v1/domains/allocation/{domain}` does return a live connection (`con_RMBLC9S3qpC6Bzv0`), so connections exist and it is the collection endpoint that is broken. Treated as an outage, not a permanent state, so the commands ship unannotated. Note this also made the command **hang past two minutes**, and chasing that produced an SDK fix. The cause was worse than a "long ladder": `de8abc2` had picked `RateLimitLinearJitterBackoff` for its `Retry-After` handling without noticing its curve, which samples uniformly over the *entire* `[1s,60s]` window and multiplies by the attempt number — so the **first** retry alone averaged ~30s and a four-retry sequence averaged over three minutes (240s worst case), nothing like the exponential-from-1s that a "1s–60s window" reads as. Retries were also invisible: the transport logged one request and one surviving response, so a four-retry sequence and one slow call produced identical output, which is exactly why this read as a hang rather than as retrying. SDK `1529d60` switches to `DefaultBackoff` plus the clamp originally intended, bounding the waits at 1+2+4+8 = 15s, and adds a `RequestLogHook`. **The CLI needs no change for either half**: it inherits the bound (measured here at 22s wall clock for the persistent 502, five attempts, down from >120s), and it already sees every attempt at `-v` because `platformVerboseTransport` wraps the `http.RoundTripper` *inside* retryablehttp's loop — the SDK's new hook logs through its own `Logger` interface, which this CLI does not set and does not need to. `jamfplatform.WithRetryPolicy` is the knob if a tighter interactive bound is ever wanted; its godoc used to describe it as a test-harness shim, which is why nothing here had found it. (`platform setup` already passes `WithRetryPolicy(0, 0, 0)`.)

**`platformVerboseTransport` labels the retries, because nothing else can.** Seeing the attempts was never the problem — the transport is below retryablehttp, so `-v` always showed all five. What was missing is that they were *retries*: five identical request/response pairs with no attempt number and no timing, which is why a bounded sequence still read as the CLI looping. The SDK's hook cannot supply it either — `Logger.LogRequest` carries only method, URL and body, so neither the attempt number nor the wait can travel through it, and setting a `Logger` here would duplicate every line for no gain. So the transport counts consecutive identical requests itself and renders `--> GET … (retry 2, waited 4.3s)`. Two guards, and the second was added after a test caught the first shipping a lie: a repeat is only a retry when the **previous attempt failed**, because retryablehttp retries nothing else — without that, a command legitimately re-issuing one request (a poll, or a `--name` lookup followed by a list of the same collection) reported `(retry 1, waited 0s)`. The rendered waits are also the cheapest confirmation that the SDK's new curve is live: 1.4s, 2.5s, 4.4s, 8.4s measured on the 502 above.

**Wire facts**, probed 2026-08-31 against the org's US credential unless noted. Everything below was run through the CLI, not just curl.

- **Three error envelopes, none of them the gateway's.** The account services answer `{classification, fields, message}` — not the gateway's `{httpStatus, traceId, errors}`, nor AI Governance's `{traceId, errors}`. The distributor `invalid_scope` is a fourth shape, `{error, error_description}`, being an OAuth error rather than a service one.
- **Three list ops declare a `{results, totalCount}` envelope and return a bare JSON array.** `GET /sso/v1/domains`, `/partners/v1/deal-registrations` and `/licensing/v1/licenses` all do. Harmless in the CLI only by luck: the generated unwrap is `if obj, ok := result.(map[string]any)`, so an array falls through unchanged. Nothing paginates, and `totalCount` never arrives.
- **Audit pages by cursor, so `--all` does not exist for it.** `GET /v1/audit` declares `page-size` + `cursor`, not `page` + `page-size`, so `hasPaginationParams` is false and the auto-pagination loop is not generated. `--page-size` and `--cursor` are plain query flags; paging is manual. `since` is the one required filter.
- `licensing/v1/licenses` returned 16 licences on this org. The **activation code is deliberately absent** from `platformTableColumns` for it: it is the value that entitles an installation, so it belongs in a JSON read someone asked for rather than in the output of a bare `list`.
- SSO domains carry statuses `VERIFIED` and `MANUALLY_VERIFIED`; `DELETE` and `actions/verify` on a bogus `domainId` answer a clean `404 "Unable to find domain by id: …"`, so those paths are exercised without touching real identity config.
- **Tokens are not portable across regions.** The same client credentials answer `401 invalid_client` at `eu.api.jamfcloud.com/auth/token`. (The earlier "tokens are portable between them" note is about the retired `apigw` host versus the GA host, not about regions.)
- **A fifth account namespace, `agreements`, is routed in prod and has no published spec.** `/agreements/v1/...` answers `403 BAD_PERMISSIONS` with a proper envelope — routed, ungranted — and `prod/api-products/account/api-definitions-external-m2m-agreements-use1.yaml` proxies it to `account.jamf.com/api-external/v1/agreements`. Nothing to ingest until a spec exists; worth knowing it is there.

**The 18 account privileges are stripped by the SDK's build, not unwritten upstream.** The published `api/account_*.json` carry no `x-required-privileges`, so the `commands -o json` catalog shows none for those 18 ops — but `public-apis-oas` declares them *twice*, inline in each team's `openapi.yaml` and again in `config.yaml` under `requiredPrivileges.operations`: `licensing:read`, `deal-registration:read`, `distributor-actions:{read,create,update}`, `sso-connections:{read,create,update,delete}`, `sso-domains:{read,create,update,delete}`. The SDK's build injects them only when `betaApiConfig.enabled` is true, and the three account specs are the only ones without that block and the only three stripped — the correlation is exact. The opt-out is correct on its own terms (`betaApiConfig` drives the beta `/{scopeType}/{scopeId}` path transform, which cannot apply to an API resolving the organization from the token); the defect is that privilege injection and path transformation share one switch, so the next API to opt out loses its metadata the same silent way. Diagnosed in the SDK's `docs/WIRE-FACTS.md` at `44a533c`. **Do not hand-supply the names here** — a local table shadows the real values the day upstream decouples the two, with nothing to notice. And do not switch source: OAS's account specs have **no `servers` block at all** and its audit spec declares `https://api.jamf.com`, so `serviceSegment` would return `""` and silently drop the namespace from every generated path. Paths, tags and response sets are otherwise identical between the two sources, and audit's `audit:read` is present in both.


### Legacy-to-DDM Payload Conversion

When `import-profile` processes a mobileconfig, compatible legacy payloads auto-convert to native DDM blueprint components instead of wrapping in `com.jamf.ddm-configuration-profile`. `--legacy` skips all conversion. Unsupported payload types filtered by default; `--include-unsupported` overrides.

Converters live in `internal/profileconvert/ddm_*.go`. Registry orchestration in `ddm_converter.go` (`ConvertToDDMComponents()`); converters register in `init()`. Current: passcode, safari, software-update deferrals, RSR, SoftwareUpdate profile. Multiple converters targeting the same component ID (e.g. deferrals + RSR + SoftwareUpdate → `software-update-settings`) deep-merge; orchestrator backfills missing scaffold sections.

Partial converters return `remaining` keys (extracted from shared payload types like `applicationaccess`); full converters return nil `remaining`. Components requiring complex schemas read base config from `blueprintcomponents.Scaffolds` at runtime, `clearIncluded()`, then overlay converted keys with `Included: true`. Jamf UI requires every section present — omitting sections blanks the panel.

Adding a converter: create `ddm_<name>.go`, implement `convertFunc`, register via `newXxxConverter()` in `ddm_converter.go` `init()`, add tests in `ddm_converter_test.go`.

## Conventions

- Global flags are package-level vars in `root.go` — accessed by generated commands via `CLIContext`.
- **Never declare a local flag whose name matches a root persistent one.** Cobra's `AddFlagSet` skips an inherited flag whose name is already taken and the *shorthand goes with it*, so a local `--dry-run` removed `-n` entirely (`unknown shorthand flag: 'n'`, exit 2) and the flag stopped appearing in that command's Global Flags list. Read the package var instead, the way `pro backup` and `protect backup` read `allowPartialFailure` and `protect restore` reads `dryRun`. Where the collision is unavoidable — `--output` on both `backup` commands is a destination directory, not an output format — the command's `Long` has to say the shorthand is gone, because `JAMF_CLI_ARGS='-o json'` is a documented CI mechanism that then exits 2. **The adjacent failure is inheriting one cleanly and then ignoring it**: a root persistent flag appears in a command's own `--help` whether the code reads it or not, so `protect backup` advertised `-n, --dry-run` and pruned files anyway — a documented flag that does nothing is worse than an absent one, because the operator used it as documented. Every command that inherits `-n` either honours it or says in its `Long` what it does not cover.
- Filename prefixes: `pro_` for Jamf Pro + Platform handwritten commands, `protect_` for Jamf Protect, `school_` for Jamf School, `security_` for Jamf Security Cloud (currently just `setup` — the eleven Risk/Device Lifecycle/SSE operations and the 47 gateway-served ones are all generator-owned). Platform uses `pro_platform_` infix where resource name overlaps with existing Pro resources.
- Help groups in `groups.go`, short aliases in `aliases.go` — each split into root / pro (including platform: `bp`, `cb`, `pdev`, `pdg`, `ddm`) / protect / school / security.
- Pro `overview` makes ~41 parallel API calls; Protect `overview` makes ~17.
- Classic API paths start with `/JSSResource/` and bypass `/api` prefix added by `client.Do()`. In platform gateway mode, rewritten to `/proclassic/` with the scope in the `X-Tenant-Id`/`X-Environment-Id` header.
- `NO_COLOR` env var respected (https://no-color.org).
- `--no-hints` flag / `JAMF_CLI_NO_HINTS` env (value-parsed via `strconv.ParseBool`) suppress advisory hints only, leaving the spinner and progress output intact; `--quiet` remains a strict superset that also silences both.
- **`--dry-run` is honoured per product, not centrally.** Jamf Pro gets it from `dryRunClient`, which wraps the `HTTPClient`; the Platform SDK client and the Security Cloud client cannot be wrapped that way, because their transports assert an exact success status and a synthetic response would have to guess 200 vs 201 vs 204 per operation. So both generators emit a `cliCtx.DryRun` check on every non-GET operation, reporting method, resolved path and body to **stderr** and returning — and `cliCtx.DryRun` is set right after the output formatter in `PersistentPreRunE`, *before* the product branches, because Protect, School and Security Cloud all return from there directly. The hand-written platform commands have no per-command preview, so `dryRunGuardTransport` refuses their writes with a 412 carrying a `DRY_RUN` code (a transport *error* would be retried by the SDK, hanging `-n` through the whole backoff ladder). A new generated resource inherits all of this; a new hand-written platform command either honours `-n` itself or is refused by the guard.
- **Never hand the platform SDK a retry client.** `jamfplatform.WithHTTPClient` assigns whatever it is given to the SDK's `retry.HTTPClient`, so an injected retryablehttp client becomes an inner retry loop whose policy wins. That is how `security uem-connectors create` came to send five POSTs after a 500 — retryablehttp retries any method, while the SDK's `isRetryableWriteStatus` deliberately refuses POST/PATCH on anything but 429/503 — and how the `traceId` went missing, since retryablehttp's default `ErrorHandler` discards the final response where the SDK's `PassthroughErrorHandler` keeps it. Pass a plain `*http.Client` carrying only the timeout, jar and the verbose/spinner transports.
- **A table's columns are the keys of its *first* row, so `omitempty` on a row field means "sometimes not a column at all".** `printTable` and `printCSV` (`internal/output/output.go`) both read `sortedKeys(rows[0])`, and `--wide` reads it too — so a field only some rows carry is a column only when the first row happens to carry it. `config list` sorts profiles alphabetically, which made one instance profile sorting first hide the scope of every platform profile below it, and hide `default` outright whenever the default profile did not sort first. The fix is per-command, not in the formatter: `listRowsForFormat` (`internal/commands/config.go`) emits a separate row type for `table`/`csv`/`plain` with no `omitempty` on the fields that must always be columns, and leaves `json`/`yaml` untouched — the same narrow-for-columns, full-for-structured split as Protect's `printResult`. Unioning keys across rows in the formatter would fix it centrally and change every table in the CLI, so it has not been done; a new list command with an optional field needs the per-command treatment or the column silently comes and goes with the sort order. `config list`'s table also shows `environment-id` and not `tenant-id` — one scope column, the level Jamf wants integrations created at — with `tenant-id` still in `-o json` for anything parsing it.
- **An empty list prints `[]`, never `null`.** All three generators aggregate paginated results into a slice and marshal it, and a nil slice marshals to `null` — so `security ztna-gateways list -o json` answered `null` on a tenant with no gateways while `dns-zones list` answered `[]` for the byte-identical wire response (`{"totalCount":0,"results":[]}`), the difference being only which spec happens to declare `page`/`page-size`. Anything piping to `jq` then failed with "Cannot iterate over null" on exactly the tenants where the collection was empty. The slices are initialised empty in `generator/platform/template.go`, `generator/security/template.go` and `generator/parser/generator.go` (the Pro one is the `list --all` path); keep it that way when touching the aggregation loops.

## Common Workflows

### Adding a feature to all generated commands

1. Edit the template `const` in `generator/parser/generator.go` (or `classic/generator.go`).
2. If new template data needed, update `parser.Resource` / `parser.Operation` in `parser/types.go`.
3. `make generate && make test && make verify-generated`.

### Syncing specs for a new Jamf Pro version

Both routes require `JAMF_PRO_VERSION` — it is written to `specs/.spec-version`, which the Makefile bakes into the binary as `specProVersion`. Full walkthrough in `docs/sync-specs.md`.

**A. Monorepo checkout:** `make sync-specs JAMF_SERVER_PATH=/path/to/jss JAMF_PRO_VERSION=11.31.0` → review `git diff --stat -- internal/commands/pro/generated/` → `make test`.

**B. Consolidated `/api/schema/` monolith:**
1. Fetch (needs auth): `curl -H "Authorization: Bearer $JAMF_TOKEN" https://<instance>/api/schema/ -o monolith.json`
2. `make sync-spec JAMF_MONOLITH_SPEC=./monolith.json JAMF_PRO_VERSION=11.31.0`
3. Review `git diff --stat -- specs/ internal/commands/pro/generated/` → `make test`.

The public monolith is a **subset** of the monorepo specs — route B legitimately drops private endpoints, which is what `PreservedSpecs` protects.

Splitter routes each path into the filename that owns it under `specs/` (path-based layout). New paths fall through to `firstTag → TagFilenameOverrides → PascalSingular(tag)`. Components classified as **exclusive** (inlined into owning file) or **shared** (emitted to `specs/_MonolithLibrary.yaml` and referenced via external $ref).

Knobs in `generator/monolith/overrides.go`:
- `TagFilenameOverrides` — explicit tag → filename map where auto-derived PascalSingular is wrong.
- `DroppedTags` — tags whose paths must never be emitted (legacy preview endpoints shadowing canonical resources).
- `PreservedSpecs` — spec files sourced outside the public monolith (private endpoints). Splitter leaves them untouched; library files they reference are auto-preserved via $ref scan.

After ingest, any **new tag** surfaces as a new resource command and trips `TestApplyProGroups_AllCommandsGrouped` — wire into the correct `proGroupMap` entry in `internal/commands/groups.go`.

### Adding a new Jamf Security Cloud endpoint

Unlike Platform, dropping a spec into `specs/.security-source/` isn't enough by itself — the eleven known operations are hand-mapped (too few and irregular for tag/family auto-detection), so a genuinely new endpoint needs a new entry too:
1. Drop/update the spec in `specs/.security-source/`, run `make sync-security-specs` to copy it into the committed `specs/security/`.
2. Add an entry to `securityOpsByFile` in `generator/parser/security.go` (resource name, operation name, `isDestructive`/`isList` as appropriate). If it's a new spec file, also add it to `SecurityScopeForFile`.
3. `make generate && make test`.
4. Wire the new resource's `New<Resource>Cmd` into `internal/commands/security.go` if it's a new resource (existing resources just gain a new operation automatically); add to `groups.go`'s `securityGroupMap`.

### Adding handwritten commands (Pro, Protect, School, Security, Platform, new product)

See the "Where to Make Changes" table for file locations. Common pattern:
1. Create new file with appropriate prefix (`pro_`, `protect_`, `school_`, `security_`, or new product's).
2. Wire into the product's bridge (`pro.go`, `protect.go`, `school.go`, `security.go`, or `root.go`).
3. Add to `groups.go` and optionally `aliases.go`.
4. For resources needing name-to-ID lookup: add resolver method in `internal/platform/resolve.go` or `internal/protect/resolve.go`.
5. Platform commands gate `RunE` with `requirePlatformClient(cliCtx)`.
6. New product namespace: also update site (`index.html`, `style.css`, `catalog.js`) — `make verify-site` enforces.
